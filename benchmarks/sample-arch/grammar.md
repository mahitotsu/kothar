# サンプル構成図に込めた文法

[handplaced.ts](handplaced.ts) で座標を手で指定して描いた図（[handplaced.svg](handplaced.svg)）について、配置と線に込めた意味を書き出す。Kothar の文法の語彙（軸、領域、線の種類、グループ、規則）を決めるための材料であり、フェーズ1で文法の記述形式を決めたら、その形式に書き直す。

## 軸

| 軸 | 意味 |
| --- | --- |
| 横（左→右） | リクエストの処理の流れ。呼び出す側が左、呼ばれる側が右 |
| 縦（上→下） | 領域を分ける。上から順に、外部サービス、本流、非同期 |

## 領域

文法はノードの名前ではなく属性を参照する。

| 領域 | 位置 | 割り当てる属性 | サンプルのノード |
| --- | --- | --- | --- |
| 上段 | 本流の上の帯 | `trust: external` | IdP、決済代行 |
| 本流 | 中央の帯 | 下の3つに当たらないもの | ユーザー、CDN、API Gateway、注文サービス、在庫サービス、注文DB、在庫DB |
| 下段 | 本流の下の帯 | `mode: async` | イベントキュー、通知ワーカー |
| 端の列 | 図の右端の列。流れの軸の外にある | `concern: cross-cutting` | ログ基盤、監視、鍵管理 |

上段のノードは、呼び出す側のノードの真上に置く。複数の呼び出す側が1つの上段のノードを呼ぶときは、上段のノードの幅を、呼び出す側すべての真上にかかるまで広げる。

## 線の種類

モデルが線に持たせるのは `kind`（`call` / `publish` / `push` / `uses`）だけで、線のスタイルと出入りの辺は、`kind` と両端の領域から文法が決める。

| 線の種類 | 条件 | スタイル | 出る辺 | 入る辺 | 経路 |
| --- | --- | --- | --- | --- | --- |
| 同期 | `call`、相手が本流 | 実線 | 右 | 左 | 本流の中で左から右へ |
| 外部呼び出し | `call`、相手が上段 | 実線 | 上 | 下 | 真上へまっすぐ |
| 非同期 | `publish` | 破線 | 下（下段へ降りる線）／右（下段の中） | 上／左 | 下段へ降り、下段の中は左から右へ |
| 逆向きの通知 | `push` | 点線、強調色 | 下 | 下 | 図の外周（下）を回って左へ戻る |
| 横断的な関心事 | `uses`、相手が端の列 | 細い点線、灰色 | 右 | 左 | 右へまっすぐ |

## グループ

| グループ | 属性 | 中身 |
| --- | --- | --- |
| VPC | `boundary: network` | API Gateway からイベントキュー、通知ワーカーまで |
| アプリ層 | `tier: app` | 注文サービス、在庫サービス |

- 横断的な関心事への線は、個々のノードからではなく VPC の右辺から出す。VPC 全体がその関心事を使う、という意味である。
- 線は不要にグループの枠を横切らない。中のノードが外のノードとつながる場合だけ横切る。

## 規則（不変条件）

リンターが検査し、エンジンのテストの正解にもなる。

1. ノード同士、ノードとラベルが重ならない。
2. 線は、線の種類ごとに決めた辺から出て、決めた辺に入る。
3. ノードは、割り当てた領域の中にある（上段 < 本流 < 下段 の縦の順序、端の列は全ノードより右）。
4. 同期の線は、出るノードが入るノードより左にある。
5. 上段のノードは、呼び出す側の真上にある（呼び出す側の中心の x 座標が、上段のノードの左右の端の間にある）。
6. 逆向きの通知の線は、通過する本流と下段のノードより下を通る。
7. 線は、両端のノードを含まないグループの枠を横切らない。
8. 線は、両端以外のノードを通らない。
9. 線は、ほかの線やグループの枠線と重ならない。交差は許す。

## 手で座標を指定して困ったこと

- ラベルの幅を見積もれず、「HTTPS」が CDN の枠に、「トークン検証」と「決済」が VPC の枠線に重なった。試し描きをして手で直した。
- API Gateway から在庫サービスへの線は、アプリ層の枠の手前（x = 535）で折る位置を手で決めた。
- 逆向きの通知の線は、VPC の下（y = 600）を通る迂回点を手で置いた。
- グループの枠は、ノードの座標に余白を足して手で計算した。ノードを動かすたびに枠も直す必要がある。
