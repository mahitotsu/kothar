# 設計の判断と理由

**この文書の読み手:** Kothar を開発する人と、使い方の理由を知りたい人。「なぜ、そう作ったのか」を一覧にする。入口は [README.md](../README.md)、規則は [SKILL.md](../skills/write-docs/SKILL.md)。

新しい判断は、末尾に足す。

| 判断 | 理由 |
|---|---|
| 雛形は `templates/` に置き、`docs/` はこのプラグイン自身の文書にする | 雛形の `<…>` が、自分の文書と混ざらない。検査も、雛形（埋め残しを許す）と自分の文書（許さない）で分けられる。 |
| 検査は、プラグインのスクリプトを直接実行する | 利用者のリポジトリに、コードも依存も足さずに済む。Node.js 24 の型の除去で動くので、ビルドも要らない。 |
| 図は、JSON の仕様から作る | 「生成するコードをリポジトリに置く」規則を、コードの複製なしで満たせる。仕様と SVG を置けば、生成物との一致を検査できる。 |
| 規則の正本は SKILL.md に置き、利用者の CLAUDE.md には写さず、スキルを参照させる | Claude が実行時に読む場所で、1 か所にしておけば、食い違わない。写しは同期の手間がかかり、原則 5（同じ内容を 2 か所に書かない）に反する。退けた案は要約の写し。スキルが発火しない小さな修正にも効くが、2 か所に書くことになる。 |
| 文書の組を選ばせ、全部は写さない | 雛形が 21 あり、使わない文書は保守の負担になる。取り組みごとに、必要な組だけを写す。 |
| 記録の文書（経過、議事録、週報、テスト結果）には日付と実績を書く | 結論と設計の文書に日付を書かない規則と、両立させる。書く場所を分け、結論へはリンクで渡す。 |
| 雛形は日本語、読み手の行の検査は Audience / Reader も受ける | 既存の方針を保ちつつ、利用者の言語で書いた文書も検査できるようにする。 |
| 埋め残しの検査は、日本語を含む `<…>` に限る | HTML のタグ（`<details>` など）を誤って拾わない。雛形の `<…>` は、日本語で書く約束にする。 |
| 規則は、5 つの原則から導き、出典つきの根拠集に置く | 規則が並ぶだけでは、迷ったときに決められない。根拠が見えれば、規則を変えるか守るかを判断できる。出典は [principles.md](principles.md)。 |
| 5 つの試験は変えず、「出す前の確認 2 つ」を足す | 原則 4（確かめられる）と 5（使える）は、形式を読む試験では確かめられない。試験の名前を変えると、既存の文書と利用者の CLAUDE.md が食い違う。 |
| 退けた案を書くのは、判断を扱う文書（設計書、設計判断、提案書）に限る | 出典（Google の設計書の指針、ADR）は、判断を扱う文書のもの。ユーザーガイドや README に書くと、使えない案が混ざり、設計判断と内容が重なる。退けた案は、すべての文書に書く一般規則だったが、範囲を限った。 |
| textlint は必須にせず、誤検知の少ない検出（冗長な表現、逆接の「が」、誇張の語、述語のあとのコロン）を自前の警告に移す。利用者が textlint を設定していれば、スキルから回す | 依存を持たず、利用者のリポジトリにも足さない方針を保つ。読点の数は、形態素解析なしでは誤検知が大半になるので移さない。退けた案は textlint の必須化。検出は確かになるが、利用者に npm の依存を足させる。 |
| textlint の設定の雛形（`templates/textlint/`）を提供する。入れるかは利用者が選ぶ | 形態素解析が要る検出（読点の数、助詞の重なり）は、textlint でしか測れない。プリセットの既定は、Kothar の文体や検査と食い違う（文の長さの数え方、太字の名前、並列の「も」）。調整した設定を配れば、利用者が組まずに済む。雛形を置くだけなので、プラグインの依存は増えない。 |
| textlint の導入の手引きは、新しいスキルにせず、write-docs の補助の文書（textlint.md）にする | 導入は 1 回きりで、手順も短い。補助の文書に分ける形は、図の手引き（figures.md）で既にある。スキルを増やすと、文書の検査で write-docs、review-docs と起動の条件が重なる。入口は、write-docs の説明に「textlint を導入するとき」を足して作る。 |
| 検査をフックで強制しない | フックは、利用者がどの Markdown を編集しても検査を走らせる。検査はスキル経由で回すという判断と食い違う。強制は確かになるが、文書でないメモの編集にも警告が出る。 |
| 太字の名前つき箇条書きは残し、使いどころを絞る | textlint の ai-writing は、機械的な印象を与える形として検出する。一方、雛形と文書の約 120 か所が、並びの項目に名前を付けるために使っている。すべて書き換える費用に見合わない。説明を分けて並べる使い方だけを、規則で止める。 |
| 日本語の自然さは、review-docs で、別のコンテキストに読ませて点検する | 語の組み合わせや段落のつながりは、規則では測れない。書いた文脈を持ち込まない読み手が要る。同じ系統のモデルの癖は見逃しうるので、最後は人が読む。 |
| 新しい検査は警告にし、`--strict` で失敗にする | 長い文や曖昧語は、誤検知がありうる。リンクなどの誤りと分け、直すか、残す理由を決められるようにする。 |
| 長い文の警告は 80 字にする | 公用文の考え方は、50〜60 字で読みにくくなっていないかを意識するよう述べる。機械の警告は、余裕を見る。 |
| 根拠の引用（`<details>`）は、文の長さの警告から外す | 出典の原文を並べる場所で、原文を短く書き換えると、引用でなくなる。 |
| 出典のない規則（数字は 1 段落に 3 個、表は 5 列）は、保ったまま「未確認」と記録する | 既存の分析から引き継いだ規則で、下げる根拠もない。出典を探す作業を残す。 |
| 図は、種類ごとの自動配置にし、手書き座標（`diagram`）を逃げ道に残す | 行・列や日付などの意味を書くだけで図ができ、レイアウトの崩れを防げる。例外の図は、手書きで描ける。 |
| 図の種類を、構造・流れの 6 種と、グラフ 8 種にする | 雛形の文書ごとに、向く図が違う（設計の流れ、企画の日程、提案の比較、週報の数字）。種類の選び方は figures.md に置く。 |
| 円グラフ、二軸、3D、虹色は作らない | 位置と長さで比べられない、または誤読を招く。出典は [principles.md](principles.md) の「図の定石」。 |
| 色で区別する系列は 3 つまで。強調（1 つだけ色を付け、残りは灰色）なら増やせる | 色の見分けやすさを優先する。GOV.UK の 4 まで、Datawrapper の 5〜7 より厳しくした。 |
| 矢印の線種に点線を足し、3 種にする。点線は 2px の丸い点で、実線と同じ濃さにする。シーケンス図には足さない | 破線（1px、薄い灰色、短い線）と同じ太さ・濃さの点線は、小さな図で見分けにくい。形・太さ・濃さの 3 つを変えた。指定は、既存の `dashed` に合わせて `dotted` にし、既存の仕様を壊さない。シーケンス図は、UML の決まり（呼び出しは実線、戻りは破線）で足りる。 |
| ラベルが収まらない入力は、クリップせず、描画をエラーにする | 切れた文字は、読めないより悪い。文字幅を見積もり、描く前に防ぐ。 |
| グラフは、隣に表を置く。表は `figure.ts --table` で作る | GOV.UK の指針と、W3C の長い説明。色や形が読めない人にも、同じ情報が届く。 |
| 状態の色（緑、黄、赤）は、記号と文字を併記し、状態にだけ使う | 色だけで伝えない（WCAG 1.4.1）。系列の色と混ぜると、意味が混線する。 |
| 例の図を、画像にして、ライトとダークで目で確かめる | 検査では、文字の重なりや矢印の向きを測れない。前回までは、画像にしていなかった。 |
| 矢印の交差は、検出して警告し、`--arrange` で自動調整する。0 件にするのは、図を作る側（エージェント）の仕事 | プラグインを使うのは、利用者に代わって文書を作るエージェント。利用者に、行と列の調整を頼む設計では、役に立たない。調整は、同じ行・列の入れ替えに限り、図の順序の意味を壊さない。 |
| 検査の呼び出しは、利用者の CLAUDE.md にパスを書かず、スキル経由にする | プラグインの場所は版ごとに変わり（キャッシュに `0.1.0`、`0.4.0` が並ぶ）、書いたパスは版が上がると古くなる。スキル内の `${CLAUDE_PLUGIN_ROOT}` は、版によらず解決される。 |
| 警告の抑制は、文書内のコメント `<!-- check-docs: 残す 理由 -->` で書き、理由を必須にする | 「残す理由を決める」を書く場所がなかった。文書の中に置けば、該当の行と一緒に動き、台帳ファイルを足さずに済む。誤りは抑えられない。理由のない抑制は警告にし、抑制した件数は検査の出力に出す。 |
| スキルの説明は、「書き始める前に使う」「既存の文書を直すときも使う」と書く。導入の手引きに、CLAUDE.md へ規則を写さないよう書く | 利用の記録では、検査スクリプトは繰り返し使われたが、手順を導くスキルは、ほとんど起動されなかった。推定: 利用者の CLAUDE.md が規則を持つと、スキルなしで書けてしまう。ログからは理由まで確かめられていない。利用の計測は、まだ持たない。 |
