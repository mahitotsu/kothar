## プレスリリース

### Kothar：構成図に込めた意図を、描き手は確実に表し、読み手は正確に読み取れるようにする

**ITアーキテクトが図の配置に込める「空間の文法」を、チームで共有できる宣言にします。どの図もその文法に従って描かれ、文法を守っているかが検査されます。**

ITアーキテクトは、構成図の配置そのものに意図を込めます。横に並べれば処理の流れ、右端の列なら横断的な関心事、上に刺さる線なら外部への呼び出し、といった具合です。しかし、この約束事は描き手の頭の中にしかありません。読み手は図ごとに約束事を推測しながら読み、描き手が込めた意図を読み落としたり、込めていない意味を読み取ったりします。描き手の側でも、意図は守りにくいものです。自動レイアウトのツールは見た目を最適化するだけで、込めた意図を配置に残しません。座標を手で指定すれば守れますが、その工夫は図ごとのコードに埋もれ、図が増え、描き手が替わるうちに約束事がぶれていきます。

Kothar では、配置の約束事を「文法」として宣言します。文法は「横は処理の流れ」「外部サービスは上段、呼び出す側の真上」「横断的な関心事は右端の列」のように、位置や線の出入りに意味を割り当てる宣言で、チームで一度書いて共有します。図ごとには、どの要素がどの意味を持つか（外部か、非同期か、横断的な関心事か、など）だけをモデルとして書きます。配置は Kothar が文法に従って決めるので、モデルに書いた意味は、必ず文法どおりの位置と線の形で図に表れます。

「外部への呼び出しを1本足せば、相手は呼び出す側の真上に置かれます。意図を配置に表すために座標と格闘する必要がなくなり、どの要素がどの意味を持つかを考えることに集中できるようになりました」と、最初の利用者であるアーキテクトは話します。

読み手も、推測せずに読めるようになります。レビューを担当するエンジニアは「どの図も同じ文法で描かれているので、文法を一度読めば、初めて見る図でも、どれが外部への呼び出しで、どれが非同期で、どれが横断的な関心事かが、位置と線の形から正確に分かります」と話します。

文法は、図が意図を正しく表しているかの検査の基準にもなります。`kothar lint` は、割り当てた領域からはみ出したノード、宣言と違う辺から出入りする線、ノードやラベルの重なりなど、意図の読み取りを妨げる配置を文法の違反として報告します。配置は文法とモデルだけで決まり、生成し直しても揺れないので、図の変更は意図の変更としてそのままレビューできます。

Kothar は npm の CLI として使えます（ファイルの拡張子と形式は仮です）。

```
npx kothar render architecture.kothar --out architecture.svg
npx kothar lint architecture.kothar
```

Claude Code のプラグインも同じリポジトリから配布します。LLM は設計書を読んで、どの要素がどの意味を持つかの下書きを作り、人はその意味の割り当てをレビューします。配置を決めるのは文法と CLI なので、LLM を使っても、図に表れる意図は文法から外れません。

## よくある質問（利用者向け）

### 描く人

**Q. 誰のためのツールですか。**
設計書を Markdown などでリポジトリに置き、図もコードで管理している IT アーキテクトのためのツールです。最初の利用者は開発者自身で、自分が実際に描く図で役に立つかを判断の基準にします。

**Q. Mermaid や D2 と何が違うのですか。**
Mermaid や D2 は、向きなど少しの指定を受けて、あとは自動で配置します。Kothar は、配置の意味（どの領域に何を置くか、線がどの辺から出入りするか）を文法として宣言し、それを守る配置を作ります。自動レイアウトのエンジン（ELK）は内部で部品として使っています。

**Q. 座標を一切書かずに済みますか。**
MVP では、座標を手で指定して描いた構成図1枚を、座標を書かずに再現することを目標にしています。どうしても文法で表せない位置には、手で位置を固定する逃げ道（ピン留め）を用意しますが、使った数を記録し、フェーズごとに減らしていきます。

**Q. 文法は自分で書く必要がありますか。**
最初はそうなります。文法はチームで一度書けば、図をまたいで使い回せます。将来は、よく使う文法をひな形として同梱することを考えています。

**Q. 同じ構成を、別の観点で描けますか。**
できるようにします。文法はノードの名前ではなく属性を参照するので、同じモデルを別の文法で描けば、リクエストの流れの図や信頼境界の図が得られます。これはフェーズ3で確かめます。

**Q. AWS などのアイコンは使えますか。**
まだ決めていません。MVP では箱とラベルだけで描きます。

**Q. 出力の形式は何ですか。**
SVG と、配置の結果（各ノードの座標と各線の経路）の JSON です。JSON は、図の差分のレビューやゴールデンテストに使います。

### 読む人

**Q. 図を読むのに Kothar を知っている必要はありますか。**
ありません。図はただの SVG です。ただ、チームの文法を一度読んでおけば、同じ文法で描かれたどの図も、位置と線の形だけで意味が読めます。

**Q. 描き手の意図を正確に読み取れることは、どう確かめるのですか。**
読み手の理解度テストで測ります。文法の説明と図を見せて「横断的な関心事はどれか」「同期の呼び出しはどれか」のような質問に答えてもらい、正答率が手で描いた図と同程度以上であることを確かめます。読み手を集められないときは、文法を知らない LLM に図を見せて答えさせ、目安にします。

**Q. 図が設計書と食い違っていないことは、どう分かるのですか。**
将来は、設計書の表（正本）とモデルを照合する検査を CI で回します。MVP には含めません。

### Claude Code で使う人

**Q. LLM に図を描かせると、生成するたびに配置が変わるのではありませんか。**
変わりません。Kothar では、LLM が書くのはモデル（要素と線と属性）の下書きだけで、座標は書きません。座標は CLI が決定論的に決めます。下書きのモデルは人がレビューします。

## よくある質問（内部向け）

**Q. 既存のツールと何が違うのですか。**
配置の意味を宣言として持ち、それを配置の制約と検査の両方に使う点です。

| ツール | 配置の決め方 | 配置の意味 | 正本との照合 |
| --- | --- | --- | --- |
| diagrams（Python）＋Graphviz | 自動配置、または座標の手指定 | 図ごとのコードに埋もれる | なし |
| Mermaid、D2 | 自動配置（向きなど少しの指定） | 扱わない | なし |
| Structurizr（C4） | 自動配置、または手で調整 | モデルとビューは分けるが、ビューは見せる要素の選択で、配置の意味は持たない | なし |
| [AWS の diagram スキル](https://pypi.org/project/awslabs.aws-diagram-mcp-server/) | LLM が diagrams のコードを書く | 生成のたびに変わる | なし |
| Kothar | 文法から決まる制約で配置 | 文法として宣言し、チームで共有する | 設計書の表と照合する |

ELK のような自動レイアウトのエンジンは、競合ではなく部品です。ISO/IEC 42010 の「ビューポイント」（どの関心事を、どの記法で描くか）に近いですが、空間の使い方まで宣言し、実行と検査ができる点が新しいところです。

**Q. 最大のリスクは何で、どこまで潰しましたか。**
「文法を守る配置をエンジンで解けるか」です。フェーズ0の検証で、サンプル図1枚については、ELK で本体を配置し、上段と端の列を文法から置く二段構成で、文法の不変条件をすべて満たしました（[検証 0001](spikes/0001-elk-layout.md)、[ADR 0001](adr/0001-layout-approach.md)）。本体の中の帯の順序を ELK で保証できない点は、まだ残っています。

**Q. なぜ PR/FAQ を確定する前に技術検証をしたのですか。**
解けないと分かってから約束を書き直すのを避けるためです。このプロジェクトの最大のリスクは、市場や利用者ではなく技術にあります。顧客への約束は Working Backwards で決め、作る順番はリスクの大きい順で決めています。

**Q. なぜ顧客を「描く人」と「読む人」の2人にしたのですか。**
最初の利用者が開発者自身なので、描く人だけを顧客にすると、PR/FAQ が自分の願望の確認で終わりやすいからです。図には、レビューする人や設計書を読む人という読み手がいます。読み手にとっての価値を約束に含めることで、意図が伝わっているかを読み手の側から測れるようになります。

**Q. 成功をどう測りますか。**
次の順で優先して測ります。

1. 文法を守っていること：文法の違反、ノードやラベルの重なりが0件で、同じ入力から同じ図が出ること。1つでも満たさなければ失敗とします。
2. 意図が伝わること：読み手の理解度テストの正答率が、手で描いた図と同程度以上であること。
3. 描き手の手間が減ること：手で位置を固定した数と、文法とモデルの記述量が、フェーズごとに減っていること。
4. 見た目が整っていること：線の交差や折れ曲がりの数を測りますが、文法より優先はしません。

**Q. MVP に含めないものは何ですか。**
構成図以外の図の種類、LLM の機能、設計書との照合、アイコンです。

**Q. 名前の由来は何ですか。**
ウガリット神話の工匠神コシャル・ワ・ハシスから取りました。バアルの宮殿を建てるとき、窓をどこに開けるかをバアルと議論した神です。
