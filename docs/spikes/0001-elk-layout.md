# 検証 0001：elkjs で文法を守る配置ができるか

- 実施日：2026-10-05
- 関連する ADR：[0001](../adr/0001-layout-approach.md)
- 検証のコード：[spikes/elk-layout/](../../spikes/elk-layout/)（elkjs 0.12.0、Node.js 24、Linux）

## 目的

文法から作った制約だけで、構成図の配置を elkjs で解けるかを確かめる。具体的には次の2つに答える。

1. 本流の左から右への流れと、線の出入りの辺を、ELK だけで守れるか。
2. 上段や端の列のような領域の指定に、ELK の外の仕組み（二段構成や制約ソルバー）が要るか。

## 方法

### 題材

[benchmarks/sample-arch/](../../benchmarks/sample-arch/) のサンプル構成図を使った。14ノード、入れ子の2グループ、14本の線からなり、座標を手で指定して描いてある（[handplaced.svg](../../benchmarks/sample-arch/handplaced.svg)）。図に込めた文法は [grammar.md](../../benchmarks/sample-arch/grammar.md) に書き出した。

モデルと文法は、記述形式が未決なので TypeScript で書いた（[model.ts](../../spikes/elk-layout/model.ts)、[grammar.ts](../../spikes/elk-layout/grammar.ts)）。文法はノードの名前を参照せず、属性と線の種類だけを参照する。

### 判定

grammar.md の7つの不変条件を、配置の結果の JSON に対して検査するリンターを書いた。

| 番号 | 規則 |
| --- | --- |
| 1 | ノード同士、ノードと線のラベルが重ならない |
| 2 | 線は、線の種類ごとに決めた辺から出て、決めた辺に入る |
| 3 | ノードは、割り当てた領域の中にある |
| 4 | 同期の線は、出るノードが入るノードより左にある |
| 5 | 上段のノードは、呼び出す側と同じ列にある |
| 6 | 逆向きの通知の線は、通過するノードより下を通る |
| 7 | 線は、両端のノードを含まないグループの枠を横切らない |

あわせて、次の2つを測った。

- 決定性：同じ入力から2回配置して、JSON がバイト単位で一致するか。別のプロセスでも一致するか。
- 安定性：本流にノードを1つ足したとき、ほかのノードの移動量の合計。

文字幅は、全角を 1em、半角を 0.6em とする見積もりで代用した。

### 試した案

| 案 | 内容 |
| --- | --- |
| A | ELK の layered（右向き、直交の経路）。グループは入れ子のノードにし（`INCLUDE_CHILDREN`）、線の出入りの辺はポートの `FIXED_SIDE` で指定する |
| B | A に、文法から計算した層（`layerChoiceConstraint`、端の列は `layerConstraint: LAST`）と層内の順序（`positionChoiceConstraint`）を足す |
| C | 入れ子をやめて平らに配置し、B の制約を足す。グループの枠はあとからメンバーを囲んで作る |
| D | 文法から粗いグリッドの座標を作り、ELK の対話モード（入力の座標を手がかりにする）に渡す |
| E | 本流と下段だけを A と同じく ELK で配置する。上段は呼び出す側の真上、端の列は全体の右に、文法から後で置く |

どの案でも、逆向きの線は ELK に向きを反転して渡し、結果の点列を戻した。理由は観察の2に書く。

## 結果

| 案 | 違反 | 内訳（規則番号:件数） | 決定性 | 1ノード追加時の移動量合計 |
| --- | --- | --- | --- | --- |
| A | 4 | 3:2 5:2 | 一致 | 487 px |
| B | 4 | 3:2 5:2 | 一致 | 487 px |
| C | 6 | 3:1 5:2 6:3 | 一致 | 28 px |
| D | 12 | 3:3 5:2 6:3 7:4 | 一致 | 71 px |
| E | 0 | なし | 一致 | 140 px |

各案の図：[A](assets/0001-elk-layout-A.svg)、[B](assets/0001-elk-layout-B.svg)、[C](assets/0001-elk-layout-C.svg)、[D](assets/0001-elk-layout-D.svg)、[E](assets/0001-elk-layout-E.svg)

案 E の図を、手で描いた元の図と並べると、要素の位置関係と線の意味は一致していた。上段は呼び出す側の真上、端の列は右端にあり、逆向きの通知は図の下を回っている。違いは、元の図ではイベントキューが在庫サービスの真下にあるのに対し、案 E では右にずれている点である。

## 観察

1. **流れの向きと線の出入りの辺は、ELK だけで守られた。** 案 A の時点で、規則2と規則4の違反は0件だった。ポートの `FIXED_SIDE` は、入れ子のグループをまたぐ線でも守られた。
2. **逆向きの線を反転せずに渡すと、本流が反転することがある。** 反転を入れる前の案 C では、ELK が閉路を壊すときに本流の線を反転し、ユーザーから API Gateway までが右から左に並んだ。
3. **層と層内順序の制約では、領域を表せなかった。** 入れ子のグラフ（案 B）では、`layerConstraint: LAST` によって上段と端の列が同じ最後の層に集まったが、違反の件数と内訳は A と同じだった。平らなグラフ（案 C）では層の指定が効いたが、上段のノードを呼び出す側と同じ層に置くと層の中の線になり、ELK はこれを満たさなかった。規則5は、ELK の中で配置した案では一度も満たされなかった。
4. **入れ子をやめると、グループの枠に無関係なノードや線が入った。** 案 C と D では、あとから作った枠の中にメンバーでないものが入った（規則7）。
5. **対話モード（案 D）は最も違反が多かった。** 層の割り当てが入力の x 座標に従うため、線の向きと食い違うと崩れた。
6. **ELK で配置した本体の外に上段と端の列を置く案 E は、7つの規則をすべて満たした。**
7. **5案とも、同じ入力から同じ JSON が出た。** 同じプロセスの2回の実行でも、別のプロセスの実行でも、バイト単位で一致した。

## 限界

- **題材は1枚だけである。** 上段への線の経路に別のノードがある構成や、上段のノードを複数の呼び出す側が共有する構成は、題材に含まれていない。
- **案 E で規則3（下段が本流より下）を満たしたのは、ELK の配置の結果であり、制約で強制したものではない。** 本体の中の帯の順序を ELK で強制する方法は見つからなかった。
- **リンターは、線が枠線の上を走ることを検出しない。** 案 E の逆向きの通知の線は、VPC の下辺に重なって走っているが、違反として数えていない。
- **決定性は Linux でしか確かめていない。**
- **文字幅は見積もりであり、実際のフォントで描くとラベルの重なりの判定が変わりうる。**
- **安定性の値には、比べる基準がない。**
- **制約ソルバーは試していない。**

## 付記：記述量

MVP の合格条件のうち「記述量」を、この題材で測った。コメントと空行を除いた行数で、手で座標を指定した [handplaced.ts](../../benchmarks/sample-arch/handplaced.ts) は87行、モデルと文法は合わせて76行（モデル48行、文法28行）だった。

ただし、比べる条件がそろっていない。

- 文法は図をまたいで使い回すので、2枚目以降の図ではモデルの行数だけが増える。
- 手で描いたほうの行数には、ラベルの重なりを直すための試し描きの手間が表れない。
- モデルと文法は、検証のために TypeScript で書いたもので、記述形式は決まっていない。
