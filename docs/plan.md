# 計画

- 最後に見直したゲート：フェーズ0

どの順で作り、何で進み具合と品質を判断するかを書く。何が終わったかは、[ゲートの記録](gates/) と git の履歴で追う。

## フェーズとゲート

フェーズはリスクの大きい順に並べる。各フェーズは [作業プロセス](process.md) の1つのサイクルに当たり、ゲートで終わる。フェーズで扱う約束は、前のフェーズのゲートで決める。

| フェーズ | 目標 | 完了条件 |
| --- | --- | --- |
| 0 | 最大のリスク（文法を守る配置をエンジンで解けるか）を確かめ、PR/FAQ を確定する | [フェーズ0のゲートの記録](gates/phase-0.md) |
| 1 | MVP（下の「MVP」を参照） | フェーズ0のゲートで決める |

フェーズ2以降は、ゲートごとに、残っているリスクの大きさで決める。今の時点で候補にしている約束と、その順を決める考え方は次のとおり。

| 候補 | 約束 | 順を決める考え方 |
| --- | --- | --- |
| 2種類目の図 | P9 | 文法という発想が汎用かどうかの分かれ目なので、MVP の次に確かめる |
| AI の機能 | P7 | モデルの形が固まってから入れる（[ADR 0003](adr/0003-ai-scope.md)） |
| 設計書との照合 | P11 | まだ決めていない |

## MVP

座標を手で指定して描いた構成図1枚を、座標を書かずに、文法と意味の割り当てだけから再現する。題材は [benchmarks/sample-arch/](../benchmarks/sample-arch/) のサンプル構成図とする。

範囲は次に限る。

- 文法の語彙：軸（流れの向き）、領域（上段、本流、端の列など）、線の種類ごとのスタイルと出入りの辺、グループ
- 図の種類：構成図だけ
- 出力：SVG と、配置の結果（座標と経路）の JSON
- 利用：CLI から。AI の機能と、設計書との照合は含めない

合格条件は、フェーズ1の要件（[docs/requirements/](requirements/) のうち `cycle: 1` のもの）とする。文法とモデルの記述量は合格条件にせず、下の「品質の評価」の「描き手の手間」で測る。

ピン留めは使ってよいが、使った数を記録する。その数を後のフェーズで減らしていく。

## テストの方針

文法そのものをテストの正解として使う。利用者の図を検査するリンターが、そのままエンジンのテストになる。

- **不変条件のテスト**：配置の結果の JSON に対して、ノードとラベルが重ならない、線が宣言した辺から出入りする、ノードが割り当てた領域に入る、軸に沿った順序が守られる、線が不要にグループの枠を横切らない、を検査する。モデルをランダムに生成するプロパティベーステスト（fast-check など）で回す。
- **決定性のテスト**：同じ入力からバイト単位で同じ JSON が出ることを、CI で Linux と macOS の両方で確かめる。
- **ゴールデンテスト**：画像ではなく、座標の JSON で取る。差分から、どのノードがどれだけ動いたかが読める。レンダラーの見た目の回帰テストは、少数だけ別に持つ。
- **安定性のテスト**：ノードや線を1つ足したとき、ほかのノードの移動量の合計が一定以下に収まることを確かめる。
- **文法の差し替えテスト**：同じモデルを別の文法で描いて、モデルを変えずに済むことを確かめる。

## 品質の評価

評価は4層に分ける。上の層ほど優先する。

| 層 | 指標 | 扱い |
| --- | --- | --- |
| 必須条件 | 文法違反、重なり、決定性 | 1つでも満たさなければ不合格 |
| 意図の伝わりやすさ | 読み手の理解度テストの正答率 | 手で描いた図と同程度なら合格 |
| 描き手の手間 | ピン留めの数、文法とモデルの行数 | フェーズごとに減っていることを確認する |
| 見た目 | 交差数、折れ曲がりの数、線の総延長、面積 | 計測するが、文法より優先しない |

理解度テストでは、文法の説明と図を見せて「横断的な関心事はどれか」「同期の呼び出しはどれか」のような質問に答えてもらい、正答率を測る。同僚に頼めないときは、文法を知らない LLM に画像を見せて答えさせ、目安にする。

評価用のデータは、これまでの検証リポジトリや銀行アプリの図を集めて作る。図ごとに文法、モデル、期待する不変条件を1組にして `benchmarks/` に置き、フェーズごとに同じデータで測る。AI の機能を入れるフェーズでは、同じデータで「設計書から作ったモデルの下書き」と「手で作ったモデル」を比べ、ノード、線、線の種類、領域の割り当てごとに適合率と再現率を測る。

## リスク

| リスク | 影響 | 対応 |
| --- | --- | --- |
| 本体の中の帯の順序（下段が本流より下）を ELK で保証できない | 文法の一部がピン留めに頼ったまま残る | ベンチマークで破れたら、制約ソルバーを検証する（[ADR 0001](adr/0001-layout-approach.md)） |
| 2種類目の図で文法の語彙が膨らむ | 文法が汎用でなく、図ごとの設定と変わらなくなる | 2種類目の図を扱うフェーズを、文法の設計を見直す区切りにする |
| 意図の伝わりやすさを測る読み手が自分しかいない | 評価が主観になる | LLM を読み手の代わりに使い、目安にする |

文字幅の計測が環境で変わるリスクは、[ADR 0006](adr/0006-text-width-measurement.md) で対応を決めた。
