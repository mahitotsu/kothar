# Kothar 企画書：空間の文法を宣言して図表を生成するツール

Oct 5, 2026 · @Kanashiki Akio

> この文書は企画書の原本をリポジトリに写したものである。原本に埋め込まれていた図（「Kotharの構成」「フェーズとゲート」）は写していないので、原本を参照すること。

## 概要

Kotharは、図の「空間の文法」を宣言し、その文法に従って構成図やコンテキスト図を決定論的に生成するツールである。文法は「横は処理の流れ」「右端の列は横断的な関心事」「同期の呼び出しは左から入る」のように、配置・方向・線の出入りに意味を割り当てる。図ごとには、どの要素がどの意味を持つかだけを書き、座標は書かない。

最初の目標は、配置を手で座標指定して描いた既存の構成図1枚を、文法と意味の割り当てだけから再現することである。配布はnpmのCLIと、Claude Codeのプラグインの2本立てとする。

名前は、ウガリット神話の工匠神コシャル・ワ・ハシスから取った。バアルの宮殿を建てるとき、窓をどこに開けるかをバアルと議論した神である。

## 背景と課題

ITアーキテクトは、図の配置そのものに意味を込める。近くに置くのは関係が深いから、縦に並べるのと横に並べるのでは意味が違う、右に刺さる線と左から出る線では役割が違う、といった具合である。この「空間の文法」は人やチームごとに少しずつ違い、多くは描き手の頭の中にしかない。

既存のツールは、この文法を扱えない。

- 自動レイアウト（Graphvizのdot、dagre、ELK）は、交差を減らす、線を短くするといった見た目の最適化をする。配置は偶然で決まり、込めた意味が失われる。
- 座標を手で指定すれば意味は守れるが、レイアウトの工夫が図ごとのコードに埋もれる。座標を指定して描いた実際の構成図では、約200行のPythonの大半が、ラベルの幅の見積もり、見えない点による余白、線の迂回点といった描画ツールの制約の回避に使われ、意図そのものは数行に散らばっていた。
- LLMに図のコードを書かせる方法（AWSのdiagramスキルなど）は既にある。実行は決定論的だが、生成は決定論的でないので、文書を直して生成し直すたびに配置が変わり、図の差分をレビューできない。

また、図の中身は設計書の表などが正本であることが多いが、図が正本と一致しているかは人の注意で守っている。

## 解決の考え方

図を「文法」と「モデル」に分ける。文法は、空間の向きや位置、線の出入りに意味を割り当てる宣言で、チームで一度だけ定義する。モデルは、図に載せる要素と線、それぞれの属性（種類、信頼レベル、所有者、同期か非同期かなど）を書く。

文法はノードの名前ではなく属性を参照する。そのため、同じモデルを別の文法で描けば、リクエストの流れの図や信頼境界の図のように、別の関心事の図が得られる。

座標は、文法から作った制約に従ってエンジンが決める。エンジンは決定論的で、同じ入力からは必ず同じ図が出る。文法は配置の制約であると同時に、検査の基準にもなる。

（図：Kotharの構成 · 入力3つ、エンジン5つの部品。原本を参照）

設計書からモデルへの破線だけがLLMの担当で、それより下はすべてCLIで再現できる。

## 利用者と利用場面

想定する利用者は、設計書をMarkdownなどでリポジトリに置き、図もコードで管理しているITアーキテクトである。最初の利用者は自分自身とし、自分が実際に描く図で役に立つかを判断の基準にする。

利用場面は次の4つを想定する。

1. 設計の変更に合わせて構成図を直す。モデルを1行直して生成し直すと、関係のない要素は動かず、図の差分がそのままレビューできる。
2. 同じ構成を、異なる関心事で描き分ける。リクエストの流れ、信頼境界、認可の連鎖、データの所有など、文法を差し替えるだけで別の図が出る。
3. CIで図を検査する。文法違反がないこと、図が設計書の正本と一致すること、コミットされた画像が再生成したものと同じことを確かめる。
4. Claude Codeで、設計書からモデルの下書きを作る。LLMは意味の割り当てだけを行い、座標は決めない。人はモデルをレビューする。

## 既存のツールとの違い

Kotharの違いは、配置の意味を宣言として持ち、それを配置の制約と検査の両方に使うことである。

| ツール | 配置の決め方 | 配置の意味 | 正本との照合 |
| --- | --- | --- | --- |
| diagrams（Python）＋Graphviz | 自動配置、または座標の手指定 | 図ごとのコードに埋もれる | なし |
| Mermaid、D2 | 自動配置（向きなど少しの指定） | 扱わない | なし |
| Structurizr（C4） | 自動配置、または手で調整 | モデルとビューは分けるが、ビューは見せる要素の選択で、配置の意味は持たない | なし |
| [AWSのdiagramスキル](https://pypi.org/project/awslabs.aws-diagram-mcp-server/) | LLMがdiagramsのコードを書く | 生成のたびに変わる | なし |
| Kothar | 文法から決まる制約で配置 | 文法として宣言し、チームで共有する | 設計書の表と照合する |

ELKのような自動レイアウトのエンジンは、競合ではなく部品である。Kotharは文法を制約に変換して、こうしたエンジンに渡す。

ISO/IEC 42010の「ビューポイント」（どの関心事を、どの記法で描くか）に近いが、空間の使い方まで宣言し、実行と検査ができる点が新しい。

## 進め方

全体はWorking Backwardsで進める。PR/FAQで「誰が、何に困っていて、Kotharで何ができるようになるか」を先に書き、要件はFAQから導き、設計と開発はフェーズごとに試行錯誤する。各フェーズの終わりに、PR/FAQの約束に近づいたかで判断する。

ただし、純粋なWorking Backwardsから2点を変える。

**1. PR/FAQと並行して、レイアウトの技術検証を先に行う。** このプロジェクトの最大のリスクは、市場や利用者ではなく「文法を守る配置をエンジンで解けるか」という技術にある。PR/FAQを固めてから解けないと分かると、約束を書き直すことになる。そこで、PR/FAQの初稿と並行して、ELKで「流れの向き」と「線の出入りの辺」だけを再現する検証を1〜2週間行い、その結果を見てPR/FAQを確定する。顧客の約束はWorking Backwardsで決め、作る順番はリスクの大きい順で決める、という分担である。

**2. 顧客を「描く人」と「読む人」の2人にする。** 最初の利用者は自分自身なので、PR/FAQが自分の願望の確認で終わりやすい。図には描き手のほかに、レビューする人や設計書を読む人という読み手がいる。読み手にとっての価値（文法を一度覚えればどの図も読める）をPR/FAQに書いておくと、品質の評価（読み手の理解度テスト）と自然につながる。

PR/FAQは書いて終わりにせず、フェーズの区切りごとに見直す。

## MVPの定義と合格条件

MVPは「座標を手で指定して描いた構成図1枚を、座標を書かずに、文法と意味の割り当てだけから再現する」ことである。題材は、ベンチマーク用にKotharのリポジトリの中で用意するサンプルの構成図とする。十数個の要素、グループ、横断的な関心事の列、本流と逆向きに迂回する線を含め、まず座標を手で指定して描いたうえで、それを再現の目標にする。

範囲は次に限る。

- 文法の語彙：軸（流れの向き）、領域（上段、本流、端の列など）、線の種類ごとのスタイルと出入りの辺、グループ
- 図の種類：構成図だけ
- 出力：SVGと、配置の結果（座標と経路）のJSON
- 利用：CLIから。LLMの機能と、設計書との照合は含めない

合格条件は次のとおり。

| 条件 | 判定 |
| --- | --- |
| 文法違反がない | リンターで0件 |
| ノードとラベルが重ならない | 座標のJSONで検査して0件 |
| 決定性 | 同じ入力から、LinuxとmacOSでバイト単位で同じJSONが出る |
| 元の図と同じ意図が読み取れる | 元の図と並べて、要素の位置関係と線の意味が一致すると自分で判断できる |
| 記述量 | 文法とモデルの合計が、同じ図を座標指定で描いたコードより大幅に少ない |

手で位置を指定する逃げ道（ピン留め）は用意するが、使った数を記録する。MVPではピン留めが残ってもよく、その数を後のフェーズで減らしていく。

## テストの方針

文法そのものをテストの正解として使う。利用者の図を検査するリンターが、そのままエンジンのテストになる。

- **不変条件のテスト**：配置の結果のJSONに対して、ノードとラベルが重ならない、線が宣言した辺から出入りする、ノードが割り当てた領域に入る、軸に沿った順序が守られる、線が不要にグループの枠を横切らない、を検査する。モデルをランダムに生成するプロパティベーステスト（fast-checkなど）で回す。
- **決定性のテスト**：同じ入力からバイト単位で同じJSONが出ることを、CIでLinuxとmacOSの両方で確かめる。文字幅はシステムのフォントに頼らず、同梱したフォントファイルのメトリクスから計測する。
- **ゴールデンテスト**：画像ではなく、座標のJSONで取る。差分から、どのノードがどれだけ動いたかが読める。レンダラーの見た目の回帰テストは、少数だけ別に持つ。
- **安定性のテスト**：ノードや線を1つ足したとき、ほかのノードの移動量の合計が一定以下に収まることを確かめる。
- **文法の差し替えテスト**：同じモデルを別の文法で描いて、モデルを変えずに済むことを確かめる。モデルを触る必要があれば、文法の情報がモデルに漏れている。

## 品質の評価

評価は4層に分ける。上の層ほど優先する。

| 層 | 指標 | 扱い |
| --- | --- | --- |
| 必須条件 | 文法違反、重なり、決定性 | 1つでも満たさなければ不合格 |
| 意図の伝わりやすさ | 読み手の理解度テストの正答率 | 手描きの図と同程度なら合格 |
| 描き手の手間 | ピン留めの数、文法とモデルの行数 | フェーズごとに減っていることを確認する |
| 見た目 | 交差数、折れ曲がりの数、線の総延長、面積 | 計測するが、文法より優先しない |

理解度テストは、文法の説明と図を見せて「横断的な関心事はどれか」「同期の呼び出しはどれか」のような質問に答えてもらい、正答率を測る。同僚に頼めないときは、文法を知らないLLMに画像を見せて答えさせ、目安にする。

評価用のデータは、これまでの検証リポジトリや銀行アプリの図を集めて作る。図ごとに文法、モデル、期待する不変条件を1組にしてベンチマークとし、フェーズごとに同じデータで測る。LLMの機能を入れるフェーズでは、同じデータで「設計書から作ったモデルの下書き」と「手で作ったモデル」を比べ、ノード、線、線の種類、領域の割り当てごとに適合率と再現率を測る。

## リポジトリの構成と配布

エンジンはClaude Codeに依存させない。描画と検査はCLIだけで完結させ、プラグインはそれを呼ぶだけにする。AIはモデルの下書きを書く道具で、決定論的な部分はAIの外に置く。

```
kothar/
├── packages/
│   ├── core/        # 文法のコンパイラ、レイアウト、レンダラー、リンター
│   └── cli/         # npx kothar render / lint / check
├── plugins/
│   └── kothar/      # Claude Codeのプラグイン（スキル、フック）
├── benchmarks/      # 評価用の図（文法、モデル、期待する不変条件）
├── docs/            # PR/FAQ、ADR、文法の仕様
└── .claude-plugin/
    └── marketplace.json
```

- 実装言語はTypeScriptとする。レイアウトにelkjsを使い、SVGを直接出力するため。
- リポジトリ自体をClaude Codeのマーケットプレイスにする。ルートの`marketplace.json`だけで配布できる。
- プラグインには、文法とモデルの書き方を教えるスキルと、モデルや文法を編集したら自動でlintと描画を走らせるフックを入れる。
- 開発中のスキルは`.claude/skills/`に置いて自分で使いながら育て、設計書からモデルを作るフェーズでプラグインに移す。

## リスクと未決事項

| リスク | 影響 | 対応 |
| --- | --- | --- |
| 「端の列」「外周を回す」などの領域の指定が、ELKだけでは表現できない | 文法の一部がピン留めに頼ったまま残る | 領域ごとにグリッドで粗く配置し、その中や間をELKで詰める二段構成を検証で試す。だめなら制約ソルバー（kiwi.jsなど）を検討する |
| 2種類目の図で文法の語彙が膨らむ | 文法が汎用でなく、図ごとの設定と変わらなくなる | フェーズ3を文法の設計を見直す区切りにする |
| 文字幅の計測が環境で変わる | 決定性が崩れる | フォントを同梱し、メトリクスをファイルから読む |
| 意図の伝わりやすさを測る読み手が自分しかいない | 評価が主観になる | LLMを読み手の代わりに使い、目安にする |

未決事項は次のとおり。

- [ ] 文法とモデルの記述形式（YAML、TypeScriptの内部DSL、独自の記法）
- [ ] 文法はノードの名前ではなく属性（種類、信頼レベル、所有者など）を参照する。モデルに持たせる属性の最小の集合
- [ ] アイコンの扱い。AWSのアイコンを同梱するか、利用者が用意するか
- [ ] ライセンス

## 最初の一歩

フェーズ0の作業は次のとおり。PR/FAQの初稿と技術検証を並行して進め、検証の結果を見てPR/FAQを確定する。

- [ ] リポジトリ`kothar`を作り、上の構成の空のディレクトリと`marketplace.json`を置く
- [ ] PR/FAQの初稿を書く。描く人と読む人の両方の顧客を書く
- [ ] ベンチマーク用のサンプルの構成図を座標指定で1枚描き、そこに込めた文法を書き出す（軸、領域、線の種類、規則）
- [ ] elkjsで、本流の左から右の流れと、線の出入りの辺だけを再現する検証をする
- [ ] 検証の結果を、ELKで足りるか、二段構成や制約ソルバーが要るかのADRにまとめる
- [ ] PR/FAQを確定し、フェーズ1に入る
