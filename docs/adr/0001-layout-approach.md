# ADR 0001: レイアウトの方式

- 状態：提案
- 日付：2026-10-05

## 背景

Kothar は、文法から作った制約に従って図を配置する（ADR 0002）。配置のエンジンを何で作るかは、このプロジェクトで最もリスクの大きい技術判断であり、文法の語彙やモデルの形より先に決める必要がある。

文法が配置に求めることは、流れの向き、線の出入りの辺、グループ、領域（上段、本流、下段、端の列）の4つである。前の3つは自動レイアウトのエンジンがもともと扱う。領域は、汎用のエンジンには対応する概念がない。

開発と保守は一人で行うので、自前で作る配置の処理が多いほど負担になる。また、[計画](../plan.md) の品質の評価では、見た目は文法より優先しない層に置いている。そのため、自前の処理の量と見た目を、文法の不変条件より低い優先度の基準にする。この2つは PR/FAQ の約束からは直接導けないので、出どころを「この ADR」とする。

## 判断の基準

優先順に並べる。

1. 図ごとの座標を書かずに、文法の不変条件を満たせること（必須）。判定：ベンチマークの図で、ピン留め（ADR 0002）を使わずに、リンターの違反が0件か。エンジンが文法の規則に従って座標を決める場合は、その規則が特定の図の形に依存しないこと。出どころ：P2、P5
2. 同じ入力から、同じ出力がバイト単位で出ること（必須）。判定：同じ入力から配置した JSON が、同じプロセスの2回の実行でも、別のプロセスの実行でも一致するか。出どころ：P6
3. 自前で作り、保守する配置の処理が少ないこと。判定：層の割り当て、交差の最小化、線の経路、グループの枠の計算のうち、自前で作るものを比べる。出どころ：この ADR
4. 見た目が整っていること。判定：線の交差の数と、折れ曲がりの数を比べる。出どころ：この ADR

## 検討した選択肢

根拠は [検証 0001](../spikes/0001-elk-layout.md) による。検証 0001 の規則6の件数は、リンターが grammar.md より広い範囲を検査していたため過大である（[フェーズ0のゲートの記録](../gates/phase-0.md)）。過大な件数を除いても、どの選択肢の評価も変わらない。

### 1. ELK だけで配置する

文法を、流れの向き、ポートの辺、入れ子のノードに変換して ELK に渡す（検証の案 A）。

- 長所：同じ入力から同じ JSON が出た（基準2）。自前で持つのは、文法を ELK の入力に変換する処理だけで済む（基準3）。
- 短所：領域を表す手段がなく、上段のノードは呼び出す側の真上に来ず、端の列も全体の右に来なかったので、違反が4件あった（基準1）。線の交差と折れ曲がりは測っていない（基準4）。

### 2. ELK に層の制約を足す

選択肢1に加えて、文法から計算した層と層内の順序を ELK の制約として渡す（案 B）。入れ子をやめて平らに配置する方法（案 C）と、文法から粗い座標を作って ELK の対話モードに渡す方法（案 D）も含む。

- 長所：同じ入力から同じ JSON が出た（基準2）。案 B は、配置がすべて ELK の中で完結する（基準3）。
- 短所：違反は案 B で4件、案 C で6件、案 D で12件あり、案 C と案 D では、グループの枠にメンバーでないものが入った（基準1）。案 C と案 D は、グループの枠を自前で計算する（基準3）。線の交差と折れ曲がりは測っていない（基準4）。

### 3. 本体を ELK で配置し、周辺の領域を文法から置く（二段構成）

本流、下段、グループからなる本体だけを選択肢1と同じく ELK で配置し、上段と端の列は本体の外に、規則（呼び出す側の真上、全体の右）に従って置く（案 E）。

- 長所：検証の題材では、違反が0件だった（基準1）。同じ入力から同じ JSON が出た（基準2）。本体の層の割り当て、交差の最小化、線の経路、グループの枠は ELK に任せられる（基準3）。
- 短所：
  - 規則5（上段の列）と、規則3のうち端の列の部分を満たしたのは、後から置く処理がその位置に置くように作られているからであり、後から置く規則が特定の図の形に依存しないかは確かめていない（基準1）。
  - 本体の中の帯の順序（下段が本流より下）は、題材では満たされたが、制約として強制できていない（基準1。検証 0001 の限界）。
  - 周辺の領域の配置と、そこへの線の経路を自前で作る（基準3）。
  - ELK の交差の最小化は周辺の領域に及ばないので、本体と周辺の間で交差が起きうるが、線の交差と折れ曲がりは測っていない（基準4）。

### 4. 制約ソルバーで配置する

文法を線形の制約に変換し、kiwi.js などで解く。

- 長所：領域や帯の順序を含めて、文法をそのまま制約として表せる見込みがあるが、確かめていない（基準1）。
- 短所：線の経路、交差の最小化、グループの枠の計算を自前で作ることになる（基準3）。決定性と見た目も確かめていない（基準2、基準4）。

## 決定

選択肢3の「二段構成」を採る見込みである。必須の基準1で「×」でない選択肢は3と4で、そのうち基準2が確かめられており、基準3でも優れるのは選択肢3である。

ただし、必須の基準1が「？」なので、文書体系の規則 S5 により承認しない。後から置く規則が特定の図の形に依存しないことを確かめるまで、提案の状態に置く。

文法のコンパイラが、モデルを本体と周辺の領域に分け、逆向きの線を反転し、線の出入りの辺をポートに変換する。本体を elkjs の layered で配置し、周辺の領域を文法の規則に従って本体の外に置く。

## 帰結

- 流れの向き、線の出入りの辺、グループ、線の経路といった重い処理は ELK に任せられる。自前で持つのは、周辺の領域の配置と、そこへの線だけで済む。
- 逆向きの線を反転して渡すことが、文法のコンパイラの責務になる。反転しないと、ELK が閉路を壊すときに本流の線を反転することがある（検証 0001 の観察2）。
- 周辺の領域の置き方（呼び出す側の真上、全体の右など）は、エンジンが固定の語彙として持ち、文法はその語彙から選ぶ。文法が周辺の領域の置き方を自由に宣言できるわけではない。
- 本体と周辺の間の交差や重なりは、リンターで検出する。
- 次のいずれかに当たれば、この決定を見直し、選択肢4を検証する。
  - 後から置く規則を、特定の図の形に依存しない語彙として書けない。
  - ベンチマークの図で、本体の中の帯の順序が破れ、ELK の範囲で直せない。
