# ADR 0001: レイアウトの方式

- 状態：承認
- 日付：2026-10-07

## 背景

Kothar は、文法から作った制約に従って図を配置する（ADR 0002）。配置のエンジンを何で作るかは、このプロジェクトで最もリスクの大きい技術判断であり、エンジンの実装を始める前に決める必要がある。

文法が配置に求めることは、流れの向き、線の出入りの辺、グループ、領域（上段、本流、下段、端の列）の4つである。前の3つは自動レイアウトのエンジンがもともと扱う。領域は、汎用のエンジンには対応する概念がない。

開発と保守は一人で行うので、自前で作る配置の処理が多いほど負担になる。また、[計画](../plan.md) の品質の評価では、見た目は文法より優先しない層に置いている。そのため、自前の処理の量と見た目を、文法の不変条件より低い優先度の基準にする。この2つは要件と約束からは直接導けないので、出どころを「この ADR」とする。

## 判断の基準

優先順に並べる。

1. 図ごとの座標を書かずに、文法の不変条件を満たせること（必須）。判定：ベンチマークの図と、形の違う図を含む検証の題材のすべてで、ピン留め（ADR 0002）を使わずに、[grammar.md](../../benchmarks/sample-arch/grammar.md) の規則1〜9の違反が0件か。出どころ：R-LAYOUT-1、R-LAYOUT-2、R-LAYOUT-3、R-LAYOUT-4、R-LAYOUT-6、R-LAYOUT-7
2. 同じ入力から、同じ出力がバイト単位で出ること（必須）。判定：同じ入力から配置した JSON が、同じプロセスの2回の実行でも、別のプロセスの実行でも一致するか。出どころ：R-DET-1
3. 自前で作り、保守する配置の処理が少ないこと。判定：層の割り当て、交差の最小化、線の経路、グループの枠の計算のうち、自前で作るものを比べる。出どころ：この ADR
4. 見た目が整っていること。判定：線の交差の数と、折れ曲がりの数を比べる。出どころ：この ADR

## 検討した選択肢

根拠は [検証 0001](../spikes/0001-elk-layout.md)、[検証 0002](../spikes/0002-post-place.md)、[検証 0003](../spikes/0003-edge-overlap.md) による。検証 0001 の違反の件数は、検証 0002 で訂正した値を使う。

### 1. ELK だけで配置する

文法を、流れの向き、ポートの辺、入れ子のノードに変換して ELK に渡す（検証 0001 の案 A）。

- 長所：同じ入力から同じ JSON が出た（基準2）。自前で持つのは、文法を ELK の入力に変換する処理だけで済む（基準3）。
- 短所：領域を表す手段がなく、上段のノードは呼び出す側の真上に来ず、端の列も全体の右に来なかったので、サンプル構成図で違反が4件あった（基準1）。線の交差と折れ曲がりは測っていない（基準4）。

### 2. ELK に層の制約を足す

選択肢1に加えて、文法から計算した層と層内の順序を ELK の制約として渡す（検証 0001 の案 B）。入れ子をやめて平らに配置する方法（案 C）と、文法から粗い座標を作って ELK の対話モードに渡す方法（案 D）も含む。

- 長所：同じ入力から同じ JSON が出た（基準2）。案 B は、配置がすべて ELK の中で完結する（基準3）。
- 短所：サンプル構成図で、違反は案 B で4件、案 C で3件、案 D で11件あり、案 C と案 D では、グループの枠にメンバーでないものが入った（基準1）。案 C と案 D は、グループの枠を自前で計算する（基準3）。線の交差と折れ曲がりは測っていない（基準4）。

### 3. 本体を ELK で配置し、周辺の領域を文法から置く（二段構成）

本流、下段、グループからなる本体を ELK で配置する。上段と端の列は本体の外に文法の規則で置き、そこへの線は、ノードとほかの線を避ける経路探索で引く（検証 0003 の案 H）。

- 長所：
  - サンプル構成図、上段のノードを共有する構成図、作業プロセスの図の3つの題材で、規則1〜9の違反が0件だった（基準1。検証 0003）。
  - 同じ入力から、同じプロセスでも別のプロセスでも、同じ JSON が出た（基準2。検証 0001、0002、0003）。
  - 本体の層の割り当て、交差の最小化、線の経路、グループの枠は ELK に任せられる（基準3）。
- 短所：
  - 後から置く規則と線の引き方を、題材の形によらないように作り直す必要があった。検証 0001 の案 E のままでは、上段のノードを共有する題材と作業プロセスの図で、線が何もないところで終わったり、ノードを貫いたりした（基準1。検証 0002）。
  - 本体の中の帯の順序（下段が本流より下）は、3つの題材では満たされたが、制約として強制できていない（基準1。検証 0001 の限界）。
  - 周辺の領域の配置と、そこへの線の経路探索を、自前で作る（基準3）。
  - 規則9を満たすために、上段のノードを共有する題材では、線が回り道をし、線の交差が1から4、折れ曲がりが18から22に増えた（基準4。検証 0003）。

### 4. 制約ソルバーで配置する

文法を線形の制約に変換し、kiwi.js などで解く。

- 長所：領域や帯の順序を含めて、文法をそのまま制約として表せる見込みがあるが、確かめていない（基準1）。
- 短所：線の経路、交差の最小化、グループの枠の計算を自前で作ることになる（基準3）。決定性と見た目も確かめていない（基準2、基準4）。

## 決定

選択肢3の「二段構成」を採る。必須の基準1と基準2の両方を満たすのは、選択肢3だけである。

文法のコンパイラが、モデルを本体と周辺の領域に分け、逆向きの線を反転し、線の出入りの辺をポートに変換する。本体を elkjs の layered で配置し、周辺の領域を文法の規則に従って本体の外に置き、そこへの線を経路探索で引く。

## 帰結

- 流れの向き、線の出入りの辺、グループ、本体の線の経路といった重い処理は ELK に任せられる。自前で持つのは、周辺の領域の配置と、そこへの線の経路探索である。
- 逆向きの線を反転して渡すことが、文法のコンパイラの責務になる。反転しないと、ELK が閉路を壊すときに本流の線を反転することがある（検証 0001 の観察2）。
- 周辺の領域の置き方（呼び出す側の真上、全体の右など）は、エンジンが固定の語彙として持ち、文法はその語彙から選ぶ。文法が周辺の領域の置き方を自由に宣言できるわけではない。
- 経路探索の費用と、規則9の間隔は、試しに決めた値のままである（検証 0003 の限界）。規則を満たすために線が回り道をし、見た目が悪くなることを受け入れる。
- 次のいずれかに当たれば、この決定を見直し、選択肢4を検証する。
  - ベンチマークの図か体験の例で、本体の中の帯の順序が破れ、ELK の範囲で直せない。
  - ベンチマークの図か体験の例で、規則1〜9の違反を0件にする経路を、経路探索で引けない線がある。
