# ADR 0011: 同梱するフォント

- 状態：承認
- 日付：2026-10-07

## 背景

ADR 0006 で、フォントファイルを同梱し、そのメトリクスで文字幅を測ると決めた。ADR 0010 で、図に使う字だけを抜き出したサブセットを SVG に埋め込むと決めた。どのフォントを同梱するかを決めないと、文字幅の計測と、SVG への埋め込みを実装できない。

## 判断の基準

優先順に並べる。

1. 図に使う日本語の字を持つこと（必須）。判定：JIS X 0208 の第1水準と第2水準の漢字をすべて持つか。出どころ：ADR 0006
2. 同梱し、サブセットを SVG に埋め込むことを、ライセンスが許すこと（必須）。判定：同梱を許すライセンスで、サブセットの名前に予約されたフォント名を使う心配がないか。出どころ：ADR 0007、ADR 0010
3. 通常の太さのサブセットを、同じ入力から同じバイト列で作れること（必須）。判定：太さ 400 の字形のサブセットを作れ、2回作って一致するか。出どころ：ADR 0010、R-DET-1
4. 配布物が小さいこと。判定：フォントのファイルの大きさを比べる。出どころ：ADR 0006

## 検討した選択肢

根拠は [検証 0004](../spikes/0004-font-metrics.md) による。3つとも、SIL Open Font License 1.1 である。

### 1. Noto Sans JP

太さを変えられる可変フォント。

- 長所：第1水準と第2水準の漢字をすべて持つ（基準1）。予約されたフォント名は「Source」で、フォントの名前に含まれない（基準2）。
- 短所：既定の太さは 100 で、太さ 400 のサブセットは fontkit で作れなかった（基準3）。ファイルは 9.4MB で、3つの中で最も大きい（基準4）。

### 2. BIZ UDPGothic

- 長所：第1水準と第2水準の漢字をすべて持つ（基準1）。予約されたフォント名がない（基準2。同梱の OFL.txt）。太さ 400 のフォントで、サブセットを作れ、同じプロセスでも別のプロセスでも同じバイト列になった（基準3）。
- 短所：ファイルは 4.6MB で、IBM Plex Sans JP の約2倍である（基準4）。

### 3. IBM Plex Sans JP

- 長所：第1水準と第2水準の漢字をすべて持つ（基準1）。太さ 400 のフォントで、サブセットを作れ、同じバイト列になった（基準3）。ファイルは 2.3MB で、3つの中で最も小さい（基準4）。
- 短所：予約されたフォント名「Plex」を持つ。サブセットの中のフォントの名前から「Plex」を除けるかは、確かめていない（基準2。[OFL FAQ](https://openfontlicense.org/ofl-faq/) の 2.6）。

## 決定

選択肢2の「BIZ UDPGothic」を採る。必須の基準1〜3をすべて満たすのは、選択肢2だけである。

## 帰結

- 文字幅を、BIZ UDPGothic のメトリクスで測る。今の見積もりとの差は、例の図のノードのラベルで最大 10.7px あった（検証 0004）。配置の結果は変わる。
- 4.6MB のフォントのファイルを、配布物に含める。ライセンスの文書（OFL.txt）を一緒に置く。
- BIZ UDPGothic が持たない字を使う図が出てきたら、この決定を見直す。
