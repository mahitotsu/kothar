# ADR 0007: ライセンス

- 状態：承認
- 日付：2026-10-06

## 背景

リポジトリを公開し、npm のパッケージと Claude Code のプラグインとして配布する前に、ライセンスを決める必要がある。依存する elkjs は EPL-2.0 で、npm の依存として利用者の環境に別に入る（ADR 0005）。同梱するフォントのライセンスとの整合も要る（ADR 0006）。

想定する利用者は、業務の図を描く IT アーキテクトである。業務で使うときに利用者が負う義務と、条文を読む手間は、使い始める妨げになる。そのため、利用者の義務、条文の長さ、特許の扱いを基準にする。これらは PR/FAQ の約束からは直接導けないので、出どころを「この ADR」とする。

## 判断の基準

優先順に並べる。

1. 公開して、利用者が使えること（必須）。判定：利用者が npm とプラグインから入手して使えるライセンスか。出どころ：P8
2. 依存と同梱物のライセンスと両立すること（必須）。判定：elkjs の EPL-2.0 と、同梱を許すフォントのライセンス（SIL Open Font License など）の条件に反しないか。出どころ：ADR 0005、ADR 0006
3. 利用者が負う義務が少ないこと。判定：利用者に課す義務（著作権表示の保持、変更の明示、ソースの公開など）の数を比べる。出どころ：この ADR
4. 条文が短く、利用者がすぐ理解できること。判定：条文の長さを比べる。出どころ：この ADR
5. 特許の扱いが明確であること。判定：特許の許諾を条文に明記しているか。出どころ：この ADR

## 検討した選択肢

### 1. MIT

[MIT License](https://opensource.org/license/mit) で公開する。

- 長所：公開して使える（基準1）。EPL-2.0 の依存とも、同梱を許すフォントのライセンスとも両立する（基準2）。利用者の義務は著作権表示の保持だけである（基準3）。条文が短く、npm のパッケージで最も一般的である（基準4）。
- 短所：特許の許諾を明記しない（基準5）。

### 2. Apache-2.0

[Apache License 2.0](https://www.apache.org/licenses/LICENSE-2.0) で公開する。

- 長所：公開して使える（基準1）。依存と同梱物のライセンスと両立する（基準2）。特許の許諾と商標の扱いを明記する（基準5）。
- 短所：著作権表示に加えて、NOTICE ファイルの保持と変更の明示を求め、利用者の義務が MIT より多い（基準3）。条文が長い（基準4）。

### 3. EPL-2.0

ELK と同じ [Eclipse Public License 2.0](https://www.eclipse.org/legal/epl-2.0/) で公開する。

- 長所：公開して使える（基準1）。ELK と扱いがそろい、ELK に手を入れて取り込む場合にも同じ条件で済む（基準2）。特許の許諾を明記する（基準5）。
- 短所：改変したファイルのソースの公開を求める弱いコピーレフトで、利用者の義務が最も多い（基準3）。条文が長い（基準4）。

### 4. まだ公開しない

ライセンスを決めずに、リポジトリを公開しないでおく。

- 長所：依存や同梱物が決まってから、それに合わせてライセンスを選べる（基準2）。
- 短所：公開しないので、利用者が使えない（基準1）。ライセンスがないので、利用者には使う許諾がなく、条文も特許の扱いもない（基準3、基準4、基準5）。

## 決定

選択肢1の「MIT」を採る。必須の基準1と2を満たす選択肢のうち、基準3で最も優れるためである。

リポジトリのルートに `LICENSE` を置き、各パッケージとプラグインのメタデータにも `MIT` を書く。

## 帰結

- 特許の許諾は明記されない。
- elkjs のソースを取り込んで改変する場合は、その部分に EPL-2.0 が残るので、別のディレクトリに分けて扱う。
- 同梱するフォントは、MIT の配布物に含められるライセンス（SIL Open Font License など）のものから選ぶ。
- 利用者や貢献者から特許の許諾の明記を求められたら、Apache-2.0 への変更を検討する。
