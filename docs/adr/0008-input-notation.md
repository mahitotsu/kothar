# ADR 0008: 文法とモデルの記述形式

- 状態：承認
- 日付：2026-10-06

## 背景

ADR 0002 で、図の入力を文法とモデルに分けると決め、記述形式は別に決めるとした。検証 0001 では、記述形式が未決だったので、文法とモデルを TypeScript のオブジェクトで書いた（[検証 0001](../spikes/0001-elk-layout.md)）。

フェーズ1の要件の検証は、どれも文法とモデルを入力にする。形式が決まらないと、エンジンの入力の読み込みも、体験の例の入力も書けないので、フェーズ1の収束のループの最初に決める。

描く人は、ある属性をなぜそのノードに割り当てたか（なぜ横断的な関心事として扱うかなど）を、モデルの中に書き残したくなる。レビューで割り当ての理由を読めるからである。これは要件や約束から直接は導けないので、コメントを書けることを基準の1つにし、出どころを「この ADR」とする。同じく、開発と保守は一人で行うので、記述形式のために自前で作る処理の量も基準にし、出どころを「この ADR」とする。

## 判断の基準

優先順に並べる。

1. 同じ文法を、複数のモデルから変えずに使えること（必須）。判定：モデルのファイルから、別のファイルにある文法を参照できるか。出どころ：R-LAYOUT-4
2. 同じ入力から同じ出力が出ること（必須）。判定：文法とモデルの中に、読み込むたびに結果が変わる処理（乱数、時刻、ファイルやネットワークの読み込み）を書けないか。出どころ：R-DET-1、R-CHECK-2、R-CHECK-3
3. 書き間違いを、Kothar の外にある汎用の道具で検査できること。判定：スキーマや型のような、形式に対して公開されている検査の仕組みがあるか。出どころ：P7、ADR 0003
4. 記述形式のために自前で作る処理が少ないこと。判定：読み込み（パーサー）、書き間違いの報告、エディタの支援のうち、自前で作るものを比べる。出どころ：この ADR
5. 割り当ての理由をコメントとして書けること。判定：形式の仕様にコメントがあるか。出どころ：この ADR
6. 図ごとに書く量が少ないこと。判定：X01 のモデルを書いたときの行数を比べる。出どころ：ADR 0002

## 検討した選択肢

### 1. YAML

文法とモデルを YAML のファイルに書く。モデルは、文法のファイルをパスで参照する。

- 長所：文法のファイルをパスで参照できる（基準1）。YAML は、データを書く記法で、関数や処理を書く構文を持たない（基準2。[YAML 1.2.2](https://yaml.org/spec/1.2.2/)）。YAML 1.2 は JSON のデータモデルを含むので、JSON Schema で検査できる（基準3。[YAML 1.2.2](https://yaml.org/spec/1.2.2/)、[JSON Schema](https://json-schema.org/)）。パーサーは既存のライブラリを使える（基準4。[yaml](https://www.npmjs.com/package/yaml)）。`#` でコメントを書ける（基準5。[YAML 1.2.2](https://yaml.org/spec/1.2.2/)）。
- 短所：JSON Schema の検査の結果を、利用者に分かる言葉の報告にする処理は、自前で作る（基準4）。X01 のモデルを YAML で書いたときの行数は、確かめていない（基準6）。

### 2. JSON

文法とモデルを JSON のファイルに書く。モデルは、文法のファイルをパスで参照する。

- 長所：文法のファイルをパスで参照できる（基準1）。JSON はデータを書く記法で、処理を書く構文を持たない（基準2。[RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)）。JSON Schema で検査できる（基準3。[JSON Schema](https://json-schema.org/)）。読み込みは JavaScript の標準の機能でできる（基準4。[JSON.parse](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/JSON/parse)）。
- 短所：JSON の仕様にはコメントがない（基準5。[RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)）。検査の結果を報告にする処理は、自前で作る（基準4）。X01 のモデルを JSON で書いたときの行数は、確かめていない（基準6）。

### 3. TypeScript の内部 DSL

文法とモデルを、TypeScript のオブジェクトとして書く。モデルは、文法のモジュールを import する。

- 長所：文法のモジュールを import で参照できる（基準1）。TypeScript の型検査で書き間違いを検査できる（基準3）。Node.js が型を除去して実行するので、読み込みの処理を作らなくてよい（基準4。[Node.js の TypeScript](https://nodejs.org/api/typescript.html)）。コメントを書ける（基準5）。検証 0001 で、X01 と同じ図のモデルを48行で書いた（基準6。[検証 0001](../spikes/0001-elk-layout.md) の付記）。
- 短所：文法とモデルはプログラムとして実行されるので、`Math.random()` や `Date.now()` のような、実行のたびに結果が変わる処理や、ファイルとネットワークの読み込みを書ける（基準2。[Math.random](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/Math/random)、[Date.now](https://developer.mozilla.org/ja/docs/Web/JavaScript/Reference/Global_Objects/Date/now)）。

### 4. 独自の記法

D2 や Mermaid のように、図のための独自の記法を作る。

- 長所：記法に処理を書く構文を入れなければ、読み込むたびに結果が変わる処理を書けない（基準2）。モデルの参照やコメントを、記法に入れられる（基準1、基準5）。
- 短所：形式に対して公開された検査の仕組みがない（基準3）。パーサー、書き間違いの報告、エディタの支援をすべて自前で作る（基準4）。X01 のモデルを書いたときの行数は、確かめていない（基準6）。

## 決定

選択肢1の「YAML」を採る。必須の基準1と2を満たすのは選択肢1、2、4で、そのうち基準3、4で選択肢4より、基準5で選択肢2より優れるためである。

## 帰結

- 文法とモデルは、データとして読むだけになり、読み込みで決定性が崩れない。
- JSON Schema を、エンジンの入力の検査と、AI がモデルを下書きするときの検査の両方に使える。
- JSON Schema の検査の結果を、利用者に分かる報告にする処理を、自前で持つ。
- 図ごとに書く行数が、TypeScript の内部 DSL より多くなるかは分かっていない。
- X01 のモデルを YAML で書いた行数が、検証 0001 の TypeScript のモデル（48行）の1.5倍を超えたら、この決定を見直す。
