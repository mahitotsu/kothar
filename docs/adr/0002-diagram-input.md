# ADR 0002: 図の入力の分け方

- 状態：提案
- 日付：2026-10-06

## 背景

ITアーキテクトは、図の配置に意味を込める。横に並べれば処理の流れ、右端の列なら横断的な関心事、上に刺さる線なら外部への呼び出し、といった具合である。既存の方法は、この意味を扱えない。

- 自動レイアウト（Graphviz の dot、dagre、ELK）は見た目を最適化するだけで、込めた意味は配置に残らない。
- 座標を手で指定すれば意味は守れるが、その工夫が図ごとのコードに埋もれる。実際の構成図では、約200行の Python の大半が、ラベル幅の見積もり、見えない点による余白、線の迂回点など、描画ツールの制約の回避に使われていた。
- AI に図のコードを書かせると、生成し直すたびに配置が変わり、図の差分をレビューできない。

Kothar の入力をどう分けるかは、ほかのすべての設計の前提になるので、最初に決める。

上の2つ目のとおり、図ごとに書く量の多さは、座標を手で指定するときの最大の負担だった。そのため、書く量を基準の1つにする。これは PR/FAQ の約束からは直接導けないので、出どころを「この ADR」とする。

## 判断の基準

優先順に並べる。

1. 配置に込めた意味を、図をまたいで使い回せること（必須）。判定：同じ意味の割り当てを、図ごとに書き直さずに複数の図に適用できるか。出どころ：P1
2. 図ごとに座標を書かずに、意味が配置に表れること（必須）。判定：図ごとの入力に座標がなくても、意味ごとに決めた位置と線の形で図が描かれるか。出どころ：P2
3. 配置が意味に従っているかを検査できること（必須）。判定：配置の結果を、入力から機械で判定できる基準が入力に含まれるか。出どころ：P5
4. 同じ入力から同じ図が出ること（必須）。判定：入力から図までの間に、生成のたびに結果が変わる処理（人や AI の判断）が入らないか。出どころ：P6
5. 同じ構成を、別の関心事の図として描き分けられること。判定：要素と線の入力を変えずに、別の配置の約束事で描けるか。出どころ：P9
6. 図ごとに書く量が少ないこと。判定：図1枚あたりに書く行数を比べる。出どころ：この ADR

## 検討した選択肢

### 1. 図ごとに座標を書く

要素と線に、図ごとに座標を与えて描く。

- 長所：座標を書けば、同じ入力から同じ図が出る（基準4）。
- 短所：配置の意味が図ごとのコードに埋もれ、ほかの図で使い回せない（基準1）。座標を書く必要がある（基準2）。意味が入力に宣言されないので、検査の基準がない（基準3）。別の関心事の図は、描き直すことになる（基準5）。描画ツールの制約を回避するコードが大半を占め、書く量が多い（基準6。背景）。

### 2. 要素と線だけを書き、自動レイアウトに任せる

Mermaid や D2 のように、要素と線を書き、配置は自動レイアウトのエンジンに任せる。

- 長所：入力に座標がなく、書く量が最も少ない（基準6）。エンジンが決定論的なら、同じ入力から同じ図が出る（基準4）。
- 短所：配置は見た目の最適化で決まり、込めた意味が配置に表れない（基準1、基準2）。意味が入力にないので、検査の基準がない（基準3）。別の関心事の図を描き分ける手段がない（基準5）。

### 3. 意味を宣言する「文法」と、要素を書く「モデル」に分ける

空間の向きや位置、線の出入りに意味を割り当てる文法と、要素と線とその属性を書くモデルに分ける。座標は、文法から作った制約に従ってエンジンが決める。

- 長所：文法は図をまたいで使い回せる（基準1）。モデルに座標を書かずに文法どおりの配置が得られ、配置をエンジンで解けることは、検証 0001 の題材で確かめた（基準2。[検証 0001](../spikes/0001-elk-layout.md)）。文法がそのまま検査の基準になる（基準3）。エンジンを決定論的にすれば、同じ入力から同じ図が出る（基準4）。
- 短所：別の関心事の図を、モデルを変えずに文法の差し替えだけで描けるかは、確かめていない（基準5）。文法を書く手間が利用者に新しく生じ、検証 0001 の題材では、モデルと文法の合計が76行、座標を手で指定したコードが87行で、図1枚では大きな差がない（基準6。[検証 0001](../spikes/0001-elk-layout.md) の付記）。

## 決定

選択肢3の「文法とモデルに分ける」を採る。必須の基準1〜4をすべて満たすのは、選択肢3だけである。

- **文法**は、空間の向きや位置、線の出入りに意味を割り当てる宣言である。チームで一度定義する。
- **モデル**は、図に載せる要素と線、それぞれの属性（種類、信頼レベル、所有者、同期か非同期かなど）を書く。座標は書かない。
- 文法はノードの名前ではなく属性を参照する。
- エンジンは決定論的にする。同じ文法とモデルからは、バイト単位で同じ配置の結果が出る。
- 文法で表せない位置には、利用者がモデルに座標を書いて固定する逃げ道を用意する。これを**ピン留め**と呼ぶ。ピン留めは使った数を記録し、減らしていく対象とする。

## 帰結

- 利用者のリンターが、そのままエンジンのテストの正解になる。文法の不変条件を満たさない配置は、エンジンの不具合である。
- 図の差分を、配置の結果の JSON の差分としてレビューできる。
- 文法を書く手間が、利用者に新しく生じる。書く量の差は、同じ文法で描く図が増えるほど大きくなる。
- 2種類目の図を扱うフェーズで、モデルを変えずに文法の差し替えだけで別の関心事の図を描けなければ、文法の情報がモデルに漏れていると判断し、文法とモデルの分け方を見直す。
