# ADR 0002: 図の入力の分け方

- 状態：承認
- 日付：2026-10-05

## 背景

ITアーキテクトは、図の配置に意味を込める。横に並べれば処理の流れ、右端の列なら横断的な関心事、上に刺さる線なら外部への呼び出し、といった具合である。既存の方法は、この意味を扱えない。

- 自動レイアウト（Graphviz の dot、dagre、ELK）は見た目を最適化するだけで、込めた意味は配置に残らない。
- 座標を手で指定すれば意味は守れるが、その工夫が図ごとのコードに埋もれる。実際の構成図では、約200行の Python の大半が、ラベル幅の見積もり、見えない点による余白、線の迂回点など、描画ツールの制約の回避に使われていた。
- LLM に図のコードを書かせると、生成し直すたびに配置が変わり、図の差分をレビューできない。

Kothar の入力をどう分けるかは、ほかのすべての設計の前提になる。

## 判断の基準

1. 配置に込めた意味を、図をまたいで共有し、検査できること
2. 同じ入力から同じ図が出ること
3. 図ごとに書く量が少ないこと
4. 同じ構成を、別の関心事の図として描き分けられること

## 検討した選択肢

### 1. 図ごとに座標を書く

- 長所：配置を完全に制御でき、意味を確実に守れる。既存の描画ツールでそのまま実現できる。
- 短所：配置の意味が図ごとのコードに埋もれ、共有も検査もできない（基準1）。描画ツールの制約を回避するコードが大半を占め、書く量が多い（基準3）。

### 2. 要素と線だけを書き、自動レイアウトに任せる

- 長所：書く量が最も少ない（基準3）。Mermaid や D2 など既存のツールで今すぐ使える。
- 短所：配置は見た目の最適化で決まり、込めた意味が残らない（基準1）。

### 3. 意味を宣言する「文法」と、要素を書く「モデル」に分ける

座標は、文法から作った制約に従ってエンジンが決める。

- 長所：文法はチームで一度書けば使い回せ、配置の制約と検査の基準を兼ねる（基準1）。モデルを変えずに文法を差し替えれば、別の関心事の図が得られる（基準4）。
- 短所：文法を書く手間が利用者に新しく生じる。文法を制約に変えて解くエンジンを自前で作る必要がある。文法で表せない配置は、ピン留めに頼ることになる。

## 決定

選択肢3を採る。

- **文法**は、空間の向きや位置、線の出入りに意味を割り当てる宣言である。チームで一度定義する。
- **モデル**は、図に載せる要素と線、それぞれの属性（種類、信頼レベル、所有者、同期か非同期かなど）を書く。座標は書かない。
- 文法はノードの名前ではなく属性を参照する。
- エンジンは決定論的にする。同じ文法とモデルからは、バイト単位で同じ配置の結果が出る。
- 文法で表せない位置には、手で位置を固定する逃げ道（ピン留め）を用意する。ただし、使った数を記録し、減らしていく対象とする。

## 帰結

- 同じモデルを別の文法で描けば、リクエストの流れの図や信頼境界の図のように、別の関心事の図が得られる。モデルを書き換えずに済まない場合は、文法の情報がモデルに漏れていると判断する。
- 利用者のリンターがそのままエンジンのテストの正解になる。文法の不変条件を満たさない配置は、エンジンの不具合である。
- 図の差分を、配置の結果の JSON の差分としてレビューできる。
- 文法を書く手間が、利用者に新しく生じる。
- モデルに持たせる属性の最小の集合と、文法とモデルの記述形式は、別に決める。
