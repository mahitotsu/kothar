# 文書体系

Kothar の文書の種類、置き場所、書き方の決まり。新しい文書を書く前に、どの種類に当たるかを決める。どれにも当たらない内容は、文書にすべきかどうかから考え直す。

## 原則

1. **1つの文書は1つの問いに答える。** 複数の問いに答えようとしている文書は分ける。
2. **凍結する記録と、更新し続ける文書を分ける。** 記録は過去の事実を書き、あとから書き換えない（誤字と壊れたリンクの修正を除く）。更新し続ける文書は今の状態だけを書き、経緯は git の履歴に任せる。
3. **根拠は参照で示し、写さない。** 同じ数値や表を複数の文書に置かない。
4. **参照は、導かれる側から導く側へ向ける。** 計画は PR/FAQ の約束から導くので、計画から PR/FAQ は参照してよいが、PR/FAQ から計画は参照しない。PR/FAQ は単独で読めるように書き、「何を約束し、何で測るか」までを書く。「どう作り、どの基準で判定するか」は計画に書く。凍結した記録（ADR、検証の報告書）は、どの文書からも根拠として参照してよい。
5. **作業項目は文書に書かない。** 「次に何をするか」は GitHub Issues で管理する。文書からは Issue を参照してよい。

## 種類

| 種類 | 何に答えるか | 書いたあと | 置き場所 |
| --- | --- | --- | --- |
| PR/FAQ | 誰に何を約束するか | 更新し続ける。ゲートごとに見直す | [prfaq.md](prfaq.md) |
| 計画 | どの順で作り、何で進み具合と品質を判断するか | 更新し続ける | [plan.md](plan.md) |
| ADR | 何をなぜそう決めたか | 凍結。覆すときは新しい ADR で置き換える | [adr/](adr/) |
| 検証の報告書 | 何を試し、何が観察されたか | 凍結 | [spikes/](spikes/) |
| ゲートの記録 | フェーズの約束に近づいたか、次に進むか | 凍結 | [gates/](gates/) |
| 仕様 | 文法とモデルの語彙と形式は、今どうなっているか | 更新し続ける | `spec/`（フェーズ1から） |
| ベンチマークの説明 | この図に込めた文法と、期待する不変条件 | データと一緒に更新する | `benchmarks/<図>/` |
| 作業項目 | 次に何をするか | 終わったら閉じる | GitHub Issues |

企画書（[proposal.md](proposal.md)）は出発点の文書で、上のどの種類にも当たらない。内容をすべて上の文書に移したら削除する（原本は git の履歴に残る）。

## 文体

| 文書 | 文体 | 理由 |
| --- | --- | --- |
| PR/FAQ | ですます調（内部向けの FAQ も含めて全体） | 顧客に向けた発表と回答の体裁を借りる文書なので。1つの文書の中で文体を混ぜない |
| それ以外 | である調 | 内部の記録で、簡潔さを優先するので |

## 各種類の書き方

### PR/FAQ

プレスリリース、利用者向けの FAQ、内部向けの FAQ の3部で書く。顧客は「描く人」と「読む人」の2人とする。冒頭に、最後に見直したゲートを書く。

### 計画

フェーズとゲート、MVP の合格条件、テストの方針、品質の評価、リスクを書く。進み具合（何が終わったか）は書かない。それはゲートの記録と Issue で分かる。

### ADR

ファイル名は `NNNN-<何を決めるかを表す短い英語>.md`、番号は通し番号。1件に決める問いは1つ。

タイトルとファイル名には、何を決めるか（問い）を書き、選んだ結果は書かない。結果がタイトルにあると、ほかの選択肢が結論ありきの比較に見えるためである。結果は「決定」の節にだけ書く。

書式は次のとおり（MADR を日本語にしたもの）。

```markdown
# ADR NNNN: <何を決めるか（名詞句）>

- 状態：提案 / 承認 / 却下 / ADR MMMM で置き換え
- 日付：YYYY-MM-DD

## 背景
何を決める必要があり、なぜ今なのか。

## 判断の基準
選択肢を比べる観点。優先順に並べる。

## 検討した選択肢
選択肢ごとに、基準に照らした長所と短所を両方書く。採らなかった選択肢にも長所を、採った選択肢にも短所を書く。根拠は検証の報告書などを参照する。

## 決定
何を選んだか。

## 帰結
この決定で得るもの、受け入れるもの、見直す条件。
```

「帰結」には作業項目を書かない。決定に伴って生じる作業は Issue にする。

### 検証の報告書

ファイル名は `NNNN-<検証の短い英語名>.md`。目的、方法、結果、観察、限界の順に書く。検証のコードは捨てる前提なので、結果を読むのに必要な図や表は報告書の側に置く（図は `spikes/assets/` に置く）。報告書は事実を書き、何を決めるかは ADR に書く。

### ゲートの記録

ファイル名は `phase-N.md`。フェーズで約束した完了条件ごとに満たしたかを書き、次のフェーズに進むかの判定と、PR/FAQ をどう見直したかを書く。

## 状態の書き方

文書の冒頭に、種類ごとに次の項目を置く。

| 種類 | 冒頭の項目 |
| --- | --- |
| PR/FAQ、計画 | 最後に見直したゲート |
| ADR | 状態、日付 |
| 検証の報告書 | 実施日、関連する ADR |
| ゲートの記録 | 判定、判定日 |
