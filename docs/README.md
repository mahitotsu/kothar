# 文書体系

Kothar の文書の種類、置き場所、書き方の決まり。新しい文書を書く前に、どの種類に当たるかを決める。どれにも当たらない内容は、文書にすべきかどうかから考え直す。どの順で文書を作り、誰が承認するかは [作業プロセス](process.md) に書く。

## 原則

1. **1つの文書は1つの問いに答える。** 複数の問いに答えようとしている文書は分ける。
2. **凍結する記録と、更新し続ける文書を分ける。** 記録は過去の事実を書き、あとから書き換えない（誤字と壊れたリンクの修正と、種類ごとの書き方に定めた例外を除く）。更新し続ける文書は今の状態だけを書き、経緯は git の履歴に任せる。
3. **根拠は参照で示し、写さない。** 同じ数値や表を複数の文書に置かない。
4. **参照は、導かれる側から導く側へ向ける。** 文書は PR/FAQ → 体験 → 要件 → 仕様の順に導く。要件から体験と PR/FAQ は参照してよいが、PR/FAQ から要件は参照しない。ADR の判断の基準、テスト、計画は要件から導くので、要件を参照する。PR/FAQ は単独で読めるように書き、「何を約束し、何で測るか」までを書く。凍結した記録（ADR、検証の報告書、ゲートの記録）は、どの文書からも根拠として参照してよい。
5. **作業項目は作業項目の一覧にだけ書く。** 「次に何をするか」は `TODO.md` で管理し、ほかの文書には書かない。更新し続ける文書からは作業項目を ID で参照してよいが、凍結する記録からは参照しない。終わった作業項目は一覧から消すので、記録からの参照が宙に浮くためである。
6. **文書の間は ID でつなぐ。** 約束、シナリオ、要件、仕様の項目には ID を振り、参照するときは ID で示す。ID は一度振ったら使い回さない。

## 種類

置き場所は、リポジトリのルートからのパスで書く。

| 種類 | 何に答えるか | 書いたあと | 置き場所 |
| --- | --- | --- | --- |
| PR/FAQ | 誰に何を約束するか | 更新し続ける。サイクルの始めとゲートでだけ変える | `docs/prfaq.md` |
| 体験 | 約束を果たしたとき、利用者は何をして何を見るか | 更新し続ける。サイクルの中では、承認のあと変えない | `docs/experience/` |
| 要件 | 何を満たせば約束を果たしたと言えるか | 更新し続ける。サイクルの中では、承認のあと変更の手続きを踏んでだけ変える | `docs/requirements.md` |
| 仕様 | 要件を満たすために、今どう作ると決めているか（仮説を含む） | 更新し続ける。項目ごとに状態を持つ | `docs/spec/` |
| 計画 | どの順で作り、何で進み具合と品質を判断するか | 更新し続ける | `docs/plan.md` |
| 作業プロセス | どの順で作業し、いつ誰が決めるか | 更新し続ける | `docs/process.md` |
| ADR | 何をなぜそう決めたか | 凍結。覆すときは新しい ADR で置き換える | `docs/adr/` |
| 検証の報告書 | 何を試し、何が観察されたか | 凍結 | `docs/spikes/` |
| ゲートの記録 | サイクルが収束したか、PR/FAQ をどう見直し、次のサイクルで何を扱うか | 凍結 | `docs/gates/` |
| ベンチマークの説明 | この図に込めた文法と、期待する不変条件 | データと一緒に更新する | `benchmarks/<図>/` |
| 作業項目 | 次に何をするか | 更新し続ける。終わった項目は消す | `TODO.md` |

## 文体

| 文書 | 文体 | 理由 |
| --- | --- | --- |
| PR/FAQ | ですます調（内部向けの FAQ も含めて全体） | 顧客に向けた発表と回答の体裁を借りる文書なので。1つの文書の中で文体を混ぜない |
| それ以外 | である調 | 内部の記録で、簡潔さを優先するので |

## 各種類の書き方

### PR/FAQ

プレスリリース、利用者向けの FAQ、内部向けの FAQ の3部で書き、最後に約束の一覧を置く。顧客は「描く人」と「読む人」の2人とする。冒頭に、最後に見直したゲートを書く。

約束の一覧は、ID、顧客、約束の3列の表とする。ID は `P1`、`P2` … と振る。本文（プレスリリースと FAQ）で利用者に約束した事柄は、すべて一覧に載せる。一覧にない事柄は約束していないものとして扱う。約束を取り下げたときは行を消し、その ID は使い回さない。

### 体験

約束ごとに、利用者の操作と見えるものをシナリオとして書く。1つのファイルに1つのシナリオを書き、ファイル名は `XNN-<シナリオの短い英語名>.md` とする（NN は2桁の通し番号）。シナリオの ID は `XNN` である。

各シナリオには、次の項目をこの順で書く。

| 項目 | 書くこと |
| --- | --- |
| 約束 | 果たす約束の ID |
| 利用者 | 描く人か、読む人か |
| 状況 | シナリオの前に、利用者がどういう状態にあるか |
| 操作 | 利用者が行うこと。コマンドや、AI エージェントへの依頼の文 |
| 見えるもの | 利用者が見る出力。図、lint の結果、ファイルの差分など |
| 例 | 入力と期待する出力の例のファイルへの参照 |

例のファイルは `docs/experience/XNN/` に置く。例は、要件の受け入れテストの入力と期待値として使う。

### 要件

`docs/requirements.md` に、要件を1件ずつ次の形で書く。

```markdown
**R-<分類>-<番号>** <要件の文>

- 出どころ：<約束の ID>、<シナリオの ID>
- 検証：<テスト / lint / 人の確認 / 読み手の理解度テスト>。<どこで、何を合格とするか>
- サイクル：<扱うフェーズの番号（例：フェーズ1）>
```

要件の文は、次のどれかの文型で書く（EARS を日本語にしたもの）。1つの文に1つの要件を書く。

| 文型 | 形 |
| --- | --- |
| 常に | <対象>は、<応答>。 |
| 事象 | <事象>とき、<対象>は、<応答>。 |
| 状態 | <状態>あいだ、<対象>は、<応答>。 |
| 望まない事象 | <望まない事象>場合、<対象>は、<応答>。 |
| 機能の有無 | <機能>を含む場合、<対象>は、<応答>。 |

要件は、どう作るかを書かない（それは仕様に書く）。「検証」には、誰が判定しても同じ結果になる合格の条件を書く。人の確認でしか判定できない要件は、何を見て、何を合格とするかを書く。

### 仕様

`docs/spec/` に、要件を満たすためにどう作るかを、項目ごとに書く。項目の ID は `S-<分類>-<番号>` とする。各項目には次を書く。

| 項目 | 書くこと |
| --- | --- |
| 状態 | 仮説 / 確定 / 廃止 |
| 満たす要件 | 要件の ID |
| 根拠 | ADR、検証の報告書、テストへの参照。仮説のあいだは空でよい |

状態を「確定」にする条件は、[作業プロセス](process.md) の「収束のループ」に従う。

### 計画

フェーズの順、テストの方針、品質の評価、リスクを書く。進み具合（何が終わったか）は書かない。それはゲートの記録と git の履歴で分かる。MVP などの合格の条件は、要件として `docs/requirements.md` に書く。

### ADR

ADR は、下の手順に従って書き、下の規則をすべて満たすようにする。規則は、誰が確かめても同じ判定になる形で書いてある。レビューでは、規則の番号を挙げて指摘する。

#### 適用の範囲

規則は、すべての ADR に当てはめる。規則に合わない承認済みの ADR は、S3 に従って提案に戻して書き直すか、S4 に従って置き換える。

#### 書く手順

次の順に進める。前の手順を終えるまで、次の手順に進まない。

1. 背景を書き、決める問いを1つに絞る。
2. 判断の基準を決める。
3. 選択肢を挙げる。
4. 根拠をそろえる。選択肢の評価に要る事実が記録（検証の報告書、ほかの ADR）にないときは、先に検証などを行って記録に書く。
5. 選択肢を評価し、対照表を作る。
6. 決定と帰結を書く。

評価を始めたあとで基準を変えたときは、すべての選択肢を評価し直す。

#### 書式

MADR を日本語にしたもの。`<>` の部分を書き換える。

```markdown
# ADR NNNN: <何を決めるか（名詞句）>

- 状態：<提案 / 承認 / 却下 / ADR MMMM で置き換え>
- 日付：<YYYY-MM-DD>

## 背景

<何を決める必要があり、なぜ今なのか>

## 判断の基準

優先順に並べる。

1. <観点>（必須）。判定：<何で判定するか>。出どころ：<要件または約束の ID、または ADR>
2. <観点>。判定：<何で判定するか>。出どころ：<要件または約束の ID、または ADR>

## 検討した選択肢

### 1. <選択肢>

<内容を1〜2文で>

- 長所：<基準に照らした長所>（基準N）
- 短所：<基準に照らした短所>（基準N）

### 2. <選択肢>

（同じ形で続ける）

### 対照表

| 選択肢 | 基準1 | 基準2 |
| --- | --- | --- |
| 1. <選択肢> | ○ | × |
| 2. <選択肢> | △ | ？ |

## 決定

<選んだ選択肢の番号と名前。どの基準で決めたか>

## 帰結

- <得るもの、受け入れるもの>
- <見直す条件>
```

#### 規則

**ファイルと冒頭**

| 番号 | 規則 |
| --- | --- |
| A1 | ファイル名は `NNNN-<何を決めるかを表す短い英語>.md`。NNNN は4桁の通し番号で、欠番を作らない。 |
| A2 | 1行目は `# ADR NNNN: <何を決めるか（名詞句）>` で、NNNN はファイル名の番号と一致する。 |
| A3 | タイトルとファイル名には問いを書き、選んだ結果を書かない。結果がタイトルにあると、ほかの選択肢が結論ありきの比較に見えるためである。 |
| A4 | タイトルの次に「状態」「日付」の2項目を、この順で置く。 |
| A5 | `##` の節は「背景」「判断の基準」「検討した選択肢」「決定」「帰結」の5つで、この順に置く。ほかの `##` の節を置かない。 |

**状態と日付**

| 番号 | 規則 |
| --- | --- |
| S1 | 状態は「提案」「承認」「却下」「ADR MMMM で置き換え」のいずれかである。 |
| S2 | 日付は、状態を最後に変えた日である。提案の ADR では、書き始めた日である。提案のあいだに内容を直しても、日付は変えない。 |
| S3 | 提案のあいだは書き換えてよい。承認した ADR は、それを根拠にした仕様、実装、ほかの ADR がないあいだは、状態を提案に戻して書き直してよい。根拠にしたものがあるかは、`docs/spec/`、コード、ほかの ADR からの参照で判定し、PR/FAQ、計画、ゲートの記録からの参照は数えない。根拠にしたものができたあとの ADR と、却下した ADR は、誤字と壊れたリンクの修正、および S4 の状態の変更を除いて書き換えない。 |
| S4 | S3 で書き直せない ADR を覆すときは、新しい ADR を書く。新しい ADR を承認したときに、古い ADR の状態を「ADR MMMM で置き換え」に変える。 |
| S5 | 必須の基準の対照表に「？」がある選択肢を選ぶときは、承認しない。状態を提案にとどめる。 |
| S6 | 必須の基準の出どころ（要件、約束、ADR）が承認されていないときは、承認しない。状態を提案にとどめる。約束は、PR/FAQ をゲートで見直したときに承認されたものとする。 |

**背景**

| 番号 | 規則 |
| --- | --- |
| G1 | 決める問いは1つである。問いが2つあれば、ADR を分ける。 |
| G2 | なぜ今決める必要があるかを書く。 |

**判断の基準**

| 番号 | 規則 |
| --- | --- |
| K1 | 基準は、書式の形の番号つきの一覧で書く。`###` の見出しで分けない。 |
| K2 | 基準は優先順に並べる。必須の基準は、必須でない基準より前に置く。 |
| K3 | 満たさない選択肢を選ばない基準には、観点の後ろに「（必須）」と書く。 |
| K4 | 「判定」には、誰が判定しても同じ結果になる事柄を書く。違反の件数、機能の有無、検証の結果などである。「少ない」「整っている」のような程度で書くときは、何を比べるかを書く。 |
| K5 | 「出どころ」には、基準を導いた要件の ID、約束の ID、またはほかの ADR を書く。どれからも導けない基準は「この ADR」と書き、背景にその理由を書く。 |
| K6 | 用語の定義を基準の中に写さない。定義している文書を参照する。定義している文書がないときは、「判定」の中で、その基準での意味を限定する。 |

**検討した選択肢**

| 番号 | 規則 |
| --- | --- |
| C1 | 選択肢ごとに `### N. <選択肢>` の見出しを置き、内容を1〜2文で書いてから、長所と短所を書く。 |
| C2 | どの選択肢にも、長所と短所を少なくとも1つずつ書く。採らなかった選択肢にも長所を、採った選択肢にも短所を書く。 |
| C3 | 長所と短所の各項目の末尾に、関係する基準の番号を「（基準N）」の形で書く。 |
| C4 | 事実を述べる項目は、根拠の記録（検証の報告書、ほかの ADR、ゲートの記録）か、公開されている外部の文書を参照する。ADR の中で新しい観察や測定の結果を書かない。 |
| C5 | 根拠の記録がない事柄は、「確かめていない」と書く。見込みを事実として書かない。 |
| C6 | 節の最後に `### 対照表` を置く。行は選択肢、列は基準で、すべての選択肢とすべての基準を含める。 |
| C7 | 対照表の記号は「○」（満たす）、「△」（一部を満たす）、「×」（満たさない）、「？」（根拠がない）の4つだけを使う。記号は、長所と短所の記述と食い違わない。 |

**決定と帰結**

| 番号 | 規則 |
| --- | --- |
| D1 | 決定には、選んだ選択肢の番号と名前、そしてどの基準で決めたかを書く。 |
| D2 | 必須の基準で「×」の選択肢を選ばない。 |
| D3 | 決定は「決定」の節にだけ書く。 |
| E1 | 帰結には、この決定で得るもの、受け入れるもの、見直す条件を書く。 |
| E2 | 見直す条件は、当たったかどうかを判定できる形で書く。 |
| E3 | 帰結に作業項目を書かない。決定に伴って生じる作業は、作業項目の一覧に加える。 |

### 検証の報告書

ファイル名は `NNNN-<検証の短い英語名>.md`。目的、方法、結果、観察、限界の順に書く。報告書は事実を書き、何を決めるかは ADR に書く。

検証のコードは `spikes/<検証の短い英語名>/` に置き、捨てる前提とする。結果の根拠（図、配置の結果、検査の結果など、検証のコードが出力したもの）は、報告書と一緒に凍結するため、`docs/spikes/evidence/<報告書のファイル名から .md を除いたもの>/` に置き、報告書からはそこを参照する。検証のコードの出力先はコミットしない。

凍結した報告書に誤りが見つかったときは、本文を書き換えず、新しい報告書の中で訂正する。訂正したら、誤りのあった報告書の冒頭に「訂正：<訂正した報告書へのリンク>」の項目を加える。

### ゲートの記録

ファイル名は `phase-N.md`（N はフェーズの番号）。次の節を、この順に置く。

| 節 | 書くこと |
| --- | --- |
| 完了条件 | 完了条件、結果、根拠の3列の表。結果は「満たした」か「満たさない」だけを書く。根拠には、満たしたことを確かめられる文書へのリンクか、「このゲートで決めたこと」の項目へのリンク（例：`[決めたこと1](#このゲートで決めたこと)`）だけを書く |
| このゲートで決めたこと | ほかの文書に置き場所がない決定を、番号つきの一覧で書く。ADR、PR/FAQ、計画などに書ける決定は、そちらに書く |
| 収束の判定 | 完了条件をすべて満たしたか。次のフェーズに進むか |
| PR/FAQ の見直し | このゲートで PR/FAQ をどう変えたか。承認済みの ADR との照合の結果 |
| 次のサイクルで扱う約束 | 次のフェーズで扱う約束の ID と理由。扱わない約束の ID と理由 |

### 作業項目

`TODO.md` に、1つの作業項目を1つの見出しで、次の形で書く。

```markdown
## T<番号>：<何をするか>

- 関連：<文書へのリンク、または ID>
- 完了条件：<終わったと判定できる条件>

<背景や詳しい内容>
```

番号は通し番号とする。一覧の冒頭に次の ID を書き、項目を加えたら1つ進める。終わった項目は消し、その番号は使い回さない。

## 状態の書き方

文書の冒頭に、種類ごとに次の項目を置く。

| 種類 | 冒頭の項目 |
| --- | --- |
| PR/FAQ | 最後に見直したゲート |
| 体験、要件 | 承認したサイクル |
| 仕様 | なし。項目ごとに状態を書く（「仕様」の節） |
| 計画、作業プロセス | 最後に見直したゲート |
| ADR | 状態、日付 |
| 検証の報告書 | 実施日、関連する ADR。訂正されたときは訂正 |
| ゲートの記録 | 判定、判定日 |
| ベンチマークの説明 | なし |
| 作業項目 | 次の ID |
