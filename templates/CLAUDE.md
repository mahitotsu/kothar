# CLAUDE.md

<題材を 1 行で。例: 小さな Web API の 2 つの実装を、性能で比べる検証>。文書の書き方は、Kothar プラグインの規則に従う（スキル `write-docs`）。

コードや git から分かることは書かない。ここには、作業の約束事と、つまずきやすい点だけを置く。

## 文書の役割（更新先を迷わないために）
読み手は <読み手を、前提知識と一緒に書く>。1 つの文書に 1 つの役割を持たせ、混ぜない。使う雛形だけを残し、下の表を自分の文書に合わせて書き替える。

| 書くこと | 更新先 |
|---|---|
| 答え 3 行、読む順番、最短の使い方 | `README.md`（入口） |
| <文書の役割> | `docs/<ファイル名>.md` |

- 人が読む文書は <文書の言語>。AI を主語にしない（「私」「Claude」「ユーザー確認済み」と書かない）。
- 日付・状況・費用の実績は、設計や結論の文書に書かない。経過、議事録、週報、テスト結果などの記録の文書に書く。

## 文書の書き方（人が読む文書は、すべてこの規則で書く）
規則は、5 つの原則から導く。迷ったら、原則に戻る。

1. **読み手に要る:** 冒頭に、読み手と目的を 1〜2 行で書く。伝えることを絞る。
2. **見つけられる:** 結論を先に書く（要旨は 3〜5 項目）。見出しは、言いたいことを書く。1 段落 1 主題、第一文に要点。1 文書 1 役割。
3. **分かる:** 1 文 1 義で、短く書く。3 つ以上の並びは箇条書き。曖昧な語を避ける。用語は初出で定義する。数字は 1 段落に 3 個まで。表は 5 列まで。図は色だけに頼らず、説明を付ける。
4. **確かめられる:** 事実・推定・意見を分ける。推定は「推定」と書き、根拠を添える。前提と、外れたときの影響を書く。
5. **使える・保てる:** 使う場面で試してから出す。同じ内容を 2 か所に書かない。持ち主を決め、変更と同じ変更で直し、古い文書は消す。

### 書き終えたら通す 5 つの試験
1. **30 秒:** タイトルと冒頭だけで、何の文書で、結論が何か分かる。
2. **見出し:** 見出しだけ読んで、筋が通る。
3. **第一文:** 各段落の第一文だけ読んで、要約になる。
4. **用語:** 初出の略語・構成名・ケース名に、定義かリンクがある。
5. **数字:** 結論の段落の数字が 3 個以内。

### 出す前の確認 2 つ
1. **根拠:** 結論の各主張に、事実か推定かの別と、根拠がある。
2. **試用:** 使う場面で試した（手順は実行した。ケースは実施できる）。試せなかったときは、そう書く。

## 検査
文書を足したり直したりしたら、Kothar の検査を通す。誤り（リンクとアンカーの行き先、表の幅、読み手の行、埋め残しの `<…>`、図）は 0 件にする。警告（長い文、曖昧語、要旨の長さ、曖昧な見出し）は、直すか、残す理由を決める。

```sh
node <Kothar のパス>/scripts/check-docs.ts          # README.md と docs/ を検査する
node <Kothar のパス>/scripts/check-docs.ts --strict # 警告も失敗にする
node <Kothar のパス>/scripts/figure.ts --check docs/figures/*.fig.json
```

## 承認が要る操作
- コミット: 区切りのよいところで、ユーザーに確認してから行う。
- 削除と、戻しにくい操作: 対象を見せて、承認を得てから行う。
- 数値、認証情報、アカウント ID、メールアドレスは、文書にもコードにも書かない。
