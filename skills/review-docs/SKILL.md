# review-docs

既存の文書を点検し、直す点を返す。書き換えは、利用者が頼んだときだけ行う。規則は、スキル `write-docs` の SKILL.md にある。

## 手順
1. **対象を決める。** 指定がなければ、`git diff` で変わった Markdown。それもなければ、README.md と `docs/`。
2. **検査を回す。** `node ${CLAUDE_PLUGIN_ROOT}/scripts/check-docs.ts <対象>` の出力を、そのまま集める。誤りと警告を分ける。図の仕様があれば `figure.ts --check` も回す。
3. **5 つの試験を当てる。** 文書ごとに、次を確かめる。
   - 30 秒: タイトルと冒頭だけで、何の文書で、結論が何か分かる。
   - 見出し: 見出しだけ読んで、筋が通る。
   - 第一文: 各段落の第一文だけ読んで、要約になる。
   - 用語: 初出の略語に、定義かリンクがある。
   - 数字: 結論の段落の数字が 3 個以内。
4. **原則 4・5 を確かめる。** 検査では測れない。
   - 根拠: 結論の各主張に、事実か推定かの別と、根拠がある。前提が書いてあり、外れたときの影響が分かる。
   - 試用: 手順は実行できるか。ケースは実施できるか。判断を求める文書は、判断に要る情報がそろっているか。
5. **役割を確かめる。** 1 文書に複数の役割が混ざっていないか。同じ内容が 2 か所にないか。結論の文書に日付や実績が入っていないか。雛形のある種類の文書は、雛形の節が欠けていないか（[catalog.md](../write-docs/catalog.md)）。
6. **返す。** 直す点を、重いものから `file:line 問題 → 直し方` の形で並べる。検査の出力、試験の判断、原則 4・5 の判断を、分けて書く。問題がなければ、そう書く。

## してはいけないこと
- 検査の出力を、再解釈して減らさない。
- 利用者が頼まないのに、文書を書き換えない。
- 読み手が分からない文書を、推測で直さない。読み手を利用者に聞く。
